# Mytest — test engineering system architecture

## Purpose

This document describes the high-level architecture for a test engineering system: hardware device drivers, the physical testbeds and DUT (device under test) that tests run against, the test case lifecycle and its Rulebook-based evaluation framework, and the telemetry engine that aggregates, stores, and evaluates telemetry post-hoc. It is intended to give an implementing agent (or engineer) enough context to build individual components without needing the design conversation that produced it.

## System context

- Single test stand. One or more supporting hardware devices (a Dewesoft DAQ, a power supply), each with its own driver process, plus the DUT itself, which also has its own driver process and command/control channel - see Process architecture. An ODrive motor controller also exists as a device type (`hardware/odrive/`) - the first *real*, non-simulated hardware in this codebase, talked to over USB - and is wired into a testbed/test case (`YdriveTestbed`/`BaseYdriveTest`) for `ydrive`, a purely mechanical DUT with no electronics of its own; see Process architecture and Open implementation decisions. A TTi CPX400DP dual-output bench power supply (`hardware/cpx400dp/`) is the second real device and the first reached over **ethernet** rather than a local bus, driven as line-oriented SCPI over a raw TCP socket. It is a driver only so far - no testbed claims it yet, so nothing declares it as a device of a run; see Open implementation decisions.
- Test cases are written in Python, each driving a test sequence through a three-phase lifecycle: PreTestSetup, MainExecution, PostTestTeardown.
- Deployment: on-prem test stand PC with network connectivity to office/cloud (not air-gapped).
- Target test-stand OS: **Windows or CentOS**. All development and testing to date has been on macOS - see OS compatibility below for the real gaps that surfaced once actually audited against the two target platforms.
- Safety requirement: some interlocks must trip in under 10ms. This is a hard real-time constraint that no process in this architecture can meet reliably (network hops, Python GC, OS scheduling all introduce unbounded jitter).

## OS compatibility

Everything in this codebase has been built and run on macOS so far; the actual test-stand deployment target is Windows or CentOS. An audit against both surfaced one significant, safety-relevant gap and a few smaller ones:

- **Graceful shutdown relied on POSIX signal semantics that don't hold on Windows - now resolved for the normal stop path.** `hardware/runner.py` installs its shutdown handler via `asyncio.add_signal_handler(SIGINT/SIGTERM, ...)` - this raises `NotImplementedError` on Windows, silently caught (`except NotImplementedError: pass`), so a hardware driver process has no signal handling installed at all on Windows; `Popen.terminate()` also calls `TerminateProcess()` there rather than sending `SIGTERM`, bypassing any signal handling that might exist anyway. This mattered because `TestCase.run()`'s own `SIGTERM` handler (`testcases/base.py`) has the identical problem: `os.kill(pid, signal.SIGTERM)`/`Popen.terminate()` on Windows both map to `TerminateProcess()`, so nothing ever reaches it externally. Fixed via `TestCase.check_stop_requested()` + `tools/stop_test.py`: a plain marker-file convention (`Path.exists()`/`.touch()`/`.unlink()`, no OS-specific code at all) checked at the same poll cadence `check_fatal_violation()` already uses, so `python -m tools.stop_test` reliably triggers `post_test_teardown()` on every target OS identically - which is what actually idles the axis (`YdriveTestbed.stop()` explicitly sends `set_axis_state("IDLE")`/disconnects over the command channel *before* terminating the driver subprocess, so it was never dependent on the subprocess's own signal handling in the first place). What this does *not* fix, and can't: Task Manager's "End Task" / a bare `taskkill /F` remains uninterceptable on Windows, exactly like `SIGKILL` on POSIX - `tools/stop_test.py` only helps if it's what's actually used to stop a test, which needs to be documented/trained practice, not something more code can enforce.
- **The operator GUI (`tools/manual_gui.py`) may not be available or usable at all on a minimal CentOS install.** `tkinter` is frequently absent from a minimal CentOS/RHEL Python install (a separate system package), and even if present, rendering a GUI window requires a display (X11/Wayland/RDP) - a headless test-stand box can't run it directly; it would need to run from a workstation pointed at the stand's endpoints instead.
- **`requires-python = ">=3.14"` is very unlikely to be available via standard CentOS package repos** (CentOS/RHEL's stock and AppStream repos lag well behind current CPython releases) - installing it will likely require a third-party repo or building from source.
- **USB access setup for the ODrive is entirely undocumented.** Nothing in the repo covers the udev rules Linux typically needs for non-root USB access, or the WinUSB/libusb driver installation (commonly via Zadig) Windows typically needs for the `odrive`/pyusb stack - this will block first-time hardware bring-up on either OS until someone works it out by hand.

Checked and found clean: no hardcoded POSIX path strings anywhere (all path construction already goes through `pathlib.Path`), no POSIX-only stdlib modules (`fcntl`/`os.fork`/`pwd`/`grp`/`pty`/`termios`), and every `subprocess.Popen` call already uses the cross-platform list-of-args form (never `shell=True`).

## Real-time tiers

Two distinct tiers, and they must not be conflated:

1. **Hard real-time (hardware tier).** Any interlock or abort that must trigger in under 10ms is implemented entirely on the device itself - for the DAQ, inside DewesoftX using its onboard Math, Alarm, and Digital-Out modules driving a hardwired relay/output to the DUT (e-stop, load release, etc.); other device types get their own onboard protection the same way (e.g. a power supply's own OVP/OCP circuitry, or the DUT's own hardware limits). Each device's hard-real-time protection runs autonomously on that device and does not depend on any process described below. This is the safety layer of record.
2. **Soft real-time (software tier).** Everything in this document — test sequencing, live limit checks, derived signal computation, evaluation, storage — operates in this tier. Acceptable latency here is roughly 10ms-1s depending on the check. Nothing in this tier should be relied on for safety-critical interlocks; it supervises and records, it doesn't replace the hardware interlock.

## Process architecture

One OS process per hardware device (including the DUT itself), plus the testcase execution process, plus the telemetry engine process - all communicating only through defined client/server and pub/sub interfaces, plus a small number of deliberate filesystem conventions (stop markers, the engine heartbeat, the run directory), and never by importing each other's internals.

**`protocol/` is the single home for anything two processes must agree on**: the wire schemas and endpoint constants (`wire.py` - `CommandRequest`/`CommandReply`, `TelemetryFrame`, `RunStateFrame`, per-device endpoints and names, the device→endpoint map, HWM sizing), the verdict record (`verdict.py`), the output layout (`paths.py`), and the engine heartbeat (`heartbeat.py`). `hardware/`, `testcases/`, `telemetry_engine/` and `testbeds/` all depend on `protocol/` and none on each other, which is the property the no-direct-imports rule actually protects. This replaced `hardware/protocol.py`, which was misfiled: the frame schema the test process publishes is a contract between it and the telemetry engine, neither of which is a hardware driver - and once the test process needed the verdict schema too, the only alternative was `testcases/` importing `telemetry_engine/`, i.e. the most upstream process importing the most downstream one.

The separation is deliberate: it lets any one process be restarted, redeployed, or rewritten independently of the others, and lets evaluation logic be tested offline against captured telemetry. With one DAQ, one power supply, and one DUT, that's five processes today; adding another device adds a sixth. The ODrive driver process is a sixth device instance, started by `YdriveTestbed` for `ydrive`'s tests (see Testbeds below) - separately from (and simultaneously runnable alongside) the DAQ/power-supply/DUT trio, since it's a wholly different DUT's test stand.

### 1. Hardware driver process (one instance per device)

This is a generic template, not device-specific code - the same command/telemetry server implementation (`hardware/command_server.py`, `hardware/telemetry_server.py`, `hardware/runner.py`) runs once per hardware device, each on its own ports, each the *only* process that talks to its device. No other process should open a second connection to the same device - a rule the CPX400DP enforces physically, since it accepts exactly one raw-socket connection and refuses a second outright. Five device types exist today, each its own subfolder under `hardware/`:

- `hardware/mock_daq/` — `MockDaqBackend`: acquisition-style sine+noise channels (`chan_temp`, `chan_pressure`, `chan_vibration`).
- `hardware/mock_power_supply/` — `MockPowerSupplyBackend`: settable output (voltage/current) + enable flag, readback with noise.
- `hardware/mock_dut/` — `MockDutBackend`: the DUT itself. A simple first-order position/velocity/current servo approximation - command channels `position_input`/`position_gain`/`velocity_gain`/`velocity_integrator`, read channels `position`/`velocity`/`current`. Proves the generic framework fits a control loop, not just readbacks.
- `hardware/odrive/` — the first *real* (non-simulated) device. Holds both `OdriveBackend` (real, talks to an actual ODrive Pro/S1 over USB via the official `odrive` PyPI package, firmware 0.6.x) and `MockOdriveBackend` (simulated, matching channel surface) side by side, unlike the three mock-only folders above. `hardware/odrive/odrive_channels.py` is deliberately *curated*, not exhaustive: 99 telemetry + 71 command channels (it grew by one when `controller_config_input_filter_bandwidth` was added back for `set_tuning_params`, then shrank by 14 once every declared channel was actually probed against real hardware - see Declared channels must exist) covering axis state/errors, motor/thermal telemetry, all three control modes plus their gains, onboard-encoder health, trajectory planner, endstops, and board/bus-level telemetry - the channels a test author would realistically set/reference or that would help diagnose a test failure. An earlier pass declared the full documented 0.6.x surface (~450/~301 channels, including internal FOC/ACIM/sensorless diagnostics, per-phase calibration coefficients, every physical encoder type, CAN config) to prove the generation approach against ODrive's whole API, then was deliberately pruned back to this set - see that module's docstring for the exact rationale. `OdriveBackend`, `MockOdriveBackend`, and `OdriveCommandClient` are all generated from one systematically-derived channel-name-to-real-attribute-path table (see `odrive_backend.py`'s module docstring), which also asserts at import time that its tables and the declared channel lists agree exactly (`_validate_channel_coverage()`) - a channel added to one and forgotten in the other fails loudly rather than silently producing an incomplete frame. `hardware/odrive/main.py` is the one entry point that isn't mock-only: it runs the real backend by default and takes a `--mock` flag to run the simulated one instead.
- `hardware/cpx400dp/` — a TTi CPX400DP dual-output bench power supply, and the first device reached over **ethernet**: line-oriented SCPI over a raw TCP socket, no vendor SDK and no new dependency. Command coverage is complete (all 66 commands in the instrument's manual); telemetry is 41 channels across **three acquisition tiers**, a distinction this device forced and the others never needed. Streamed channels (8 queries per frame) are measurements or state the instrument changes by itself. Cached channels are settings only this driver writes - read at connect, refreshed after a command that changes them, then carried in every frame from memory. The third tier is *not* telemetry at all: the read-and-clear error registers, which the driver consumes itself after every write, because this instrument accepts writes it then silently discards (an out-of-range setpoint leaves the value untouched, answers nothing, and reports itself only in `EER?`). Unlike `hardware/odrive/`, there is **no mock backend**: this driver's risk is response parsing rather than device paths, so a backend-level mock would replace the code most likely to be wrong. Tests substitute the *transport* instead, against byte-exact replies transcribed from the real instrument. `connect()`/`disconnect()` are deliberately passive - they adopt whatever output state they find and hand it back unchanged. See `hardware/README.md` for the measured behaviour, including several points where the instrument contradicts its own manual.

Each instance owns a `HardwareBackend` that requires only a universal core - `connect`, `disconnect`, `get_status`, `stream_samples`, `list_actions` - plus one generic `execute(action, **params)` for anything device-specific. The command/telemetry server code never needs to know what actions a given device supports, so adding a new device type never requires touching the server - only a new backend implementation under its own `hardware/mock_<device>/` folder (and, for caller convenience, a thin named-method wrapper on the client side, e.g. `hardware/mock_dut/mock_dut_command_client.py`'s `DutCommandClient`). `hardware/odrive/odrive_backend.py` proves this same interface holds against a real device talking real USB, not just another simulation - its blocking `odrive` package calls are wrapped in `asyncio.to_thread(...)` so they don't stall the command/telemetry servers sharing its event loop.

Exposes two interfaces:

- **Command server** — request/reply. Accepts commands from whoever needs to talk to that device (the testbed, the DUT abstraction, or a test case directly) and executes them against the device: the four universal actions (`connect`/`disconnect`/`get_status`/`list_actions`) go straight to the backend's core methods, everything else routes to `execute()` unchanged.
- **Telemetry server** — pub/sub. Streams the raw, decoded, timestamp-aligned live channel data at full rate. Does no evaluation or transformation beyond decode and timestamp alignment — it must stay fast enough that it never becomes the bottleneck. Channel names/values are an arbitrary dict, so this needs no changes at all across device types.

### 2. Testbeds — the physical fixture, not the DUT

`testbeds/<device_under_test>/` (e.g. `testbeds/example_testbed/`) defines the *supporting instrument* hardware a DUT's tests run against - today, one DAQ and one power supply. It deliberately does **not** start or command the DUT's own driver process - that's a distinct concern, owned instead by the DUT abstraction (below). `ExampleTestbed` is a context manager (`with ExampleTestbed() as testbed: ...`) that launches/tears down the DAQ and power supply driver processes as a unit, so test cases and demos don't each duplicate that subprocess-launching boilerplate. It also owns a ready-to-use, connected `PowerSupplyCommandClient` (`testbed.power_supply`) - instantiating and starting the testbed is the one thing a test case needs to get control of its supporting test hardware, rather than separately constructing its own power supply client alongside it.

### 3. The DUT abstraction — the product under test's own command and control

`testcases/<dut>/dut/` (e.g. `testcases/example_dut/dut/example_dut.py`'s `ExampleDut`) is the abstraction over the DUT's *own* hardware command and control channel - separate from the instruments the testbed manages. It owns the DUT driver process's lifecycle (start/stop, as a context manager) and is the *one* façade test-authored code touches for that DUT: every command/telemetry channel gets its own named `get_<channel>()`/`set_<channel>()` method (e.g. `set_position()`, `get_position()`, `get_velocity()`, `get_current()`), even where that's a thin forward to the underlying command/telemetry client - see Design principles. `get_channels()` returns a single, consistent snapshot of every read channel from one instant (via a telemetry subscription dedicated to synchronous point-reads, kept separate from the one handed to `LiveRulebookRunner`'s background thread, since a ZeroMQ socket isn't safe to read from two threads at once); the per-channel getters are thin wrappers over it. `start()` positively confirms the backend's declared channels actually exist - see Channel declaration below. A test case typically starts both the testbed (instruments) and the DUT (product) in PreTestSetup, and stops both in PostTestTeardown.

**Channel declaration** (`hardware/mock_<device>/mock_channels.py`): each backend declares its own `TELEMETRY_CHANNELS`/`COMMAND_CHANNELS` - the source of truth for what it actually streams/accepts, right next to the code that produces/accepts those exact strings (not a hand-maintained list elsewhere that could drift). `ExampleDut.start()` positively confirms both against the *live* driver process - `TelemetryClient.verify_channels()` blocks for one real frame and checks its keys; `CommandClient.verify_actions()` calls the backend's own `list_actions()` (a new addition to the universal core, dispatched the same way as `connect`/`disconnect`/`get_status`) and checks its answer - raising `MissingChannelError` immediately in `PreTestSetup` if either is missing, rather than a test discovering the gap later when some step happens to use the missing channel. `testcases/<dut>/channels.py` re-exports the same lists (not a second, independently-maintained copy) purely as a one-stop reference for test authors. Only wired up for the DUT today - DAQ and power supply have their own `mock_channels.py` declared, but nothing calls `verify_channels()`/`verify_actions()` against them yet, since no test case watches their telemetry (see Open implementation decisions).

**When there's no separate DUT: ydrive.** The testbed-vs-DUT split above assumes the DUT has its own electronics/driver process, distinct from the instruments around it. `ydrive` (`testbeds/ydrive_testbed/`, `testcases/ydrive/`) doesn't fit that assumption: it's a purely mechanical unit under test with no electronics of its own - the ODrive motor controller (`hardware/odrive/`) that drives it is the *entire* hardware interface, both actuator and sensor. So `YdriveTestbed` (unlike `ExampleTestbed`) owns the ODrive driver process directly and exposes `testbed.command`/`testbed.telemetry` - there's no separate `testcases/ydrive/dut/` façade, and test steps use the testbed's clients directly rather than through a second wrapper layer. `YdriveTestbed.start()` still positively confirms the ODrive's declared channels the same way `ExampleDut.start()` does. This is a deliberate architectural deviation for this one DUT, not a new default pattern - a future DUT with its own electronics should still follow the `ExampleTestbed`/`ExampleDut` split above.

`BaseYdriveTest` (`testcases/ydrive/testcases/base_ydrive_test.py`) is the bones-only base case, same role as `BaseExampleDutTest`: starts the testbed, tags its telemetry via the Telemetry Publisher, and has a no-op `main_execution()` - proving the setup/teardown/tagging plumbing works before any real test sequence exists. Unlike `BaseExampleDutTest`, it splits Rulebook evaluation into two deliberately separate steps: `pre_test_setup()` *constructs* a `LiveRulebookRunner` against `RULEBOOKS` (populated with `YDRIVE_RULEBOOK` - `testcases/ydrive/rulebooks/ydrive_rulebook.py`, two real fatal bounds - see below) but does **not** call `.start()` on it - a concrete subclass decides when live evaluation actually begins, by calling `self.runner.start(self.testbed.telemetry)` itself from wherever in its own `main_execution()` that should happen (e.g. only once the axis is armed and commanded, not while it's still idle). `post_test_teardown()` always calls `self.runner.stop()` regardless of whether a subclass ever called `start()` - `LiveRulebookRunner.stop()` is a safe no-op if its background thread was never started. `use_mock` is plumbed through from `BaseYdriveTest`/`YdriveTestbed`'s constructors down to `hardware/odrive/main.py --mock`, defaulting to `False` (real hardware) since the whole point of this DUT is running against a real ODrive - `testcases/demo_ydrive_test_run.py` passes `use_mock=True` explicitly, since it demonstrates the Telemetry Publisher's tagging plumbing rather than exercising real hardware - a real ODrive is now available and used directly via `EnduranceCycleTest`/`ManualTest` instead (see below and Resolved implementation decisions). `testcases/ydrive/teststeps/teststeps.py` holds two test steps. `cycle_position`: one full low<->high position cycle (command, closed-loop-block via `testbed.get_pos_estimate()`/`get_vel_estimate()` until within `position_tolerance` AND settled to within `velocity_tolerance`, dwell, repeat for the other target), raising `TimeoutError` if a target isn't reached within `arrival_timeout_s` rather than silently returning - a stuck/faulted axis is a real failure, not a quietly-shortened test. Unlike `example_dut`'s `cycle_position`, it takes no overall `duration_s` and doesn't loop internally - it's a single building block a concrete test's `main_execution()` calls repeatedly to build a longer cycling test, and it assumes the axis is already armed (control mode + axis state) before it runs. `dwell_s`/`position_tolerance`/`velocity_tolerance`/`arrival_timeout_s` all have convenience defaults now (still setup-dependent placeholders, not physically-validated numbers - override them for the actual mechanism). `set_tuning_params`: sets the controller's velocity limit, position filter bandwidth, position/velocity/velocity-integrator gains, and spinout power thresholds in one call, defaulting to a named tuning profile (`MAX_LOAD_VELOCITY_LIMIT`, `MAX_LOAD_FILTER_BW`, etc.) rather than generic "default" constants. Both steps use `test_case.check_fatal_violation()`/`wait_for()` for the fatal-violation polling described in Design principles/Open implementation decisions. `YdriveTestbed` gained `get_channels()`/`get_pos_estimate()`/`get_vel_estimate()` and a second `sync_telemetry` client for this - the same closed-loop point-read pattern as `ExampleDut`'s `_sync_telemetry`, added only once an actual step needed it.

A concrete test case now exists: `EnduranceCycleTest` (`testcases/ydrive/testcases/testcases.py`) cycles ydrive indefinitely between two position setpoints - no fixed duration or cycle count, running until a fatal Rulebook violation or external stop - tracking cumulative distance traveled (`total_distance_m` state) computed analytically from the known setpoints (`2 * |HIGH_POSITION - LOW_POSITION| * METERS_PER_TURN`, 0.084 m/turn) rather than measured from telemetry. Its `main_execution()` starts `self.runner` *before* issuing any command to the ODrive (tuning params, control mode, axis state), so live evaluation is watching from the very first command onward, not just once cycling begins. Verified end-to-end against `MockOdriveBackend`: `set_tuning_params`' values land correctly (confirmed via telemetry readback - note `get_channels()`/`sync_telemetry` can return a few already-buffered/stale ZMQ SUB frames immediately after a burst of setup calls before catching up to the live value, which is expected socket-backlog behavior, not a bug), and `EnduranceCycleTest` run for several real cycles accumulated `total_distance_m` exactly as expected (e.g. 0.336m -> 0.672m over two 2-turn cycles), with teardown completing cleanly even while a cycle was still in flight.

`ManualTest` (same file) is the second concrete ydrive test case, and has no test sequence of its own: it starts live Rulebook evaluation, then blocks via `self.wait_for(float("inf"))` - the same `check_fatal_violation()` polling every other step already relies on (`Stopwatch.POLL_INTERVAL_S`'s 10ms cadence), so it aborts on a fatal bound just as promptly as any other test. This keeps the ODrive driver process and its command/telemetry endpoints alive for an operator to command/view directly - see Operator tooling below. It deliberately leaves the axis in `IDLE`, unconfigured (no tuning, no control mode, no arming): that choice belongs to the operator in the moment, not to this test case. `post_test_teardown()` is inherited unchanged from `BaseYdriveTest` for the same reason - it has no idea where the operator left the axis, so it doesn't command any move, just idles it.

`YDRIVE_RULEBOOK` (`testcases/ydrive/rulebooks/ydrive_rulebook.py`) now has two real fatal bounds: `overcurrent_bound` (`board_ibus` > 30A for 5s continuous - `persistence_s` debounces a brief spike, e.g. during a fast direction reversal) and `undervoltage_bound` (`board_vbus_voltage` < 10.5V, no persistence - trusted instantaneously). `Rulebook.test_name` became `Rulebook.test_names` (a list), so one Rulebook's bounds can be shared across more than one concrete test case instead of matching exactly one `TestCase.TEST_NAME` - `YDRIVE_RULEBOOK.test_names` lists both `"endurance_cycle_test"` and `"manual_test"`, matching `EnduranceCycleTest`/`ManualTest`'s own `TEST_NAME`s exactly.

### 4. Testcase execution process

`testcases/` holds both the reusable framework and the concrete, per-DUT test content:

- **Framework** (top level of `testcases/`): `base.py` (`TestCase`, the abstract three-phase lifecycle ABC), `state_publisher.py` (`RunStatePublisher`), `utils.py` (`Stopwatch`, see below, plus `spawn_operator_dashboard` - see Operator tooling), and `asimov/` (the Rulebook evaluation framework, see next section).
- **Per-DUT content**: `testcases/<dut>/testcases/` (concrete `TestCase` subclasses), `testcases/<dut>/rulebooks/` (concrete `Rulebook`s), `testcases/<dut>/dut/` (the DUT abstraction).

Each test case is implemented as a three-phase lifecycle, not a generic state machine:

- **PreTestSetup** — start the testbed (instruments) and the DUT, power the DUT via the testbed's power supply, seed this run's state channels, and wire up a `LiveRulebookRunner` with this test's Rulebook(s). The run itself was already announced before this phase began: `run()` starts the `RunStatePublisher` first, so the telemetry engine knows which run is open, and which devices it claims, before any driver process exists. `BaseExampleDutTest` implements exactly this and nothing else - it's directly runnable, with a no-op `MainExecution`, proving the setup/teardown/tagging/evaluation-wiring plumbing works before any real test sequence exists. Concrete test cases subclass it (e.g. `CycleDutPositionTest`) and override `MainExecution` (and `TEST_NAME`/`RULEBOOKS`).
- **MainExecution** — the test's own sequence logic. `LiveRulebookRunner` owns telemetry consumption and Rulebook evaluation entirely on its own background thread (started/stopped by `BaseExampleDutTest`); a test step's own code (e.g. `CycleDutPositionTest`'s `cycle_position` step, in `testcases/example_dut/teststeps/teststeps.py`) is a plain elapsed-time loop that never touches a telemetry frame, a channels dict, or evaluation at all - it paces itself via `for _ in clock:` (`Stopwatch.__iter__`, see below), and only ever calls `dut.get_position()` (a synchronous point-read through `ExampleDut`'s façade, not a telemetry subscription) to closed-loop-check arrival. A non-fatal bound's violation is logged and the test continues. A fatal bound's violation stops `LiveRulebookRunner`'s own evaluation (it raises internally and its background thread exits); `TestCase`'s shared `@step` decorator checks for it at this step's entry and exit too (see the open decision on the resulting gap), but `CycleDutPositionTest`'s `cycle_position` runs the entire cycling sequence inside one single step call, so in practice that only means "checked before the test starts and after it's already finished" - it doesn't poll internally the way `ydrive`'s `cycle_position` does. `CycleDutPositionTest` cycles the DUT's commanded position between two setpoints for a fixed duration: after commanding a target, it blocks (via `dut.get_position()`) until actually within `position_tolerance` of that target - not just after a fixed timeout - then holds there for `dwell_s` before flipping. The currently commanded setpoint is published as `position_target` state purely for visibility - no Bound references it today (see Asimov below and the open decision on dynamic-reference Bounds).
- **PostTestTeardown** — return the system to a state where another test can start (stop the DUT, disable/disconnect the power supply, stop the testbed, stop the telemetry publisher). Always runs, unconditionally, regardless of how PreTestSetup or MainExecution ended (normal completion, a fatal breach, a partway-through setup failure, or any other unexpected exception) - there's no "skip teardown" case. Because PreTestSetup sets up multiple devices sequentially, it can fail partway through, so PostTestTeardown must check what was actually set up before tearing it down. Each teardown action also runs independently of the others (a shared `teardown_step()` helper logs a failure rather than raising), so one device's cleanup failing can't prevent another's, and can't mask whatever exception is already propagating out of PreTestSetup or MainExecution.

**Recording is a precondition for the test.** A run's whole product is its record, and both real-hardware test cases run indefinitely, so a test that keeps moving hardware after recording has stopped spends real mechanical wear producing nothing recoverable. `TestCase.run()` therefore calls `require_recording_started()` before `pre_test_setup()` and refuses to start if the telemetry engine isn't recording, and `check_recording_alive()` polls the engine's heartbeat at the *same* call sites `check_fatal_violation()`/`check_stop_requested()` already use (`wait_for()`'s 10 ms tick, `@step`'s entry/exit), raising `RecordingLost` - handled by `run()`'s `try/finally` exactly like `StopRequested`. It inherits the same known gap: a long step that never polls won't notice until it returns. `require_engine=False` opts out entirely, for the five demo scripts that deliberately run with no engine (three of them acting as their own consumer) and for unit tests.

Two behaviours here are deliberate and were both corrected after being observed for real against a mock ydrive run:

- **The check switches off once teardown begins.** Teardown steps go through `@step` like any other, so a dead engine would otherwise abort each individual teardown step - leaving the axis un-idled, precisely the state teardown exists to prevent. By then the verdict is already written, so liveness has nothing left to protect.
- **`RecordingLost` does not linger.** Lingering (see Operator status page below) exists so an operator can read a final result off the status page; a recorder dying mid-run is unattended infrastructure failure, and the point of aborting was to stop consuming hardware - which a process hanging on a `Ctrl+C` nobody is there to press defeats.

This is deliberately *not* the same rule as a silent telemetry stream (see Timeout watchdogs), which is fatal because it means losing live *safety monitoring* while hardware may still be moving. Monitoring is unaffected by recording loss - the `LiveRulebookRunner` keeps evaluating from its own subscription throughout. What's lost is the run's product, so the argument is economic rather than safety-critical.

**Stopping a running test case.** `TestCase.run()` converts `SIGTERM` into the same clean-teardown path `Ctrl+C` already gets for free via Python's default `SIGINT` → `KeyboardInterrupt` handling. Without this, `kill <pid>` (the default signal an external supervisor/systemd/CI would send to stop an unattended run) terminates the process immediately, skipping `post_test_teardown()` entirely - for a test case with no fixed duration (`EnduranceCycleTest`, `ManualTest`) that means real hardware gets abandoned exactly where it was, axis never idled, driver subprocess orphaned instead of disconnected. Discovered by actually sending a running test process `SIGTERM` and watching neither happen. Only registered when `run()` executes on the main thread - `signal.signal()` raises `ValueError` otherwise, and this codebase already calls `TestCase.run()` off the main thread in three places (`telemetry_engine/demo_evaluation_run.py`/`demo_storage_run.py`/`demo_aggregator_run.py`, via `asyncio.to_thread()`) - silently skipped there rather than crashing, since those demos exercise a no-op `main_execution()` for a few seconds, not an unattended, physically-moving run.

`SIGTERM` doesn't reliably reach a process on Windows, though (see OS compatibility) - `tools/stop_test.py` is the OS-independent alternative: it leaves a plain marker file that `TestCase.check_stop_requested()` polls for at the exact same call sites `check_fatal_violation()` already uses, raising `StopRequested` (handled identically by `run()`'s `try/finally`). `python -m tools.stop_test` with no arguments discovers whichever test is currently running via the run-state stream, so an operator never needs to already know its auto-generated `test_id`. This coexists with, rather than replaces, the `SIGTERM` path above - `kill <pid>` keeps working exactly as before on POSIX.

**Operator status page.** `run()` also spawns a lightweight, locally-hosted status page (`testcases/utils.py`'s `spawn_operator_dashboard()`, implemented in `tools/operator_dashboard.py` - see Operator tooling below) before `pre_test_setup()` even starts, so it's up to show an error even if setup itself crashes. Its header reads "Mytest Status: Running/Complete/Aborted" (`"Mytest"` in the brand's purple), and it reflects exactly how `run()`'s own `try/except` resolves: `"running"` while the test is active, `"passing"`/`"failing"` on completion (shown as a "Result: Pass/Fail" line and a light green/red page background), `"stopped"` (not a failure, no result line) for a deliberate `StopRequested`/`SIGTERM`-driven `SystemExit`, with the exception shown for `"failing"`. While `"running"`, the color and result line instead track the Rulebook's own *live* `test_status` off the run-state stream - a non-fatal bound violating doesn't raise anything (see `check_fatal_violation()`), so this is the only way the page can show red before the test itself reaches a conclusion. A large ASCII animation in the page's center - a bouncing `-` while running, a plain `X` once it isn't - gives an at-a-glance running/not-running signal independent of color. The page's only interaction is a "Stop test" button, itself just `tools/stop_test.py`'s own `request_stop()` - there is deliberately no way to send a command through it, unlike `tools/manual_gui.py`.

Once the test is over, `run()` blocks (`_wait_until_interrupted()`) so this final result stays visible rather than disappearing the instant the test completes - a daemon thread (the dashboard's server) dies with its process regardless of whether it's explicitly stopped, so "persisting" the page genuinely requires keeping the process itself alive. Ended by `Ctrl+C`/`SIGTERM` in that terminal, or by `tools/stop_test.py --test-id <id>` again - explicit `--test-id` only, since `stop_test.py`'s no-argument auto-discovery relies on the run-state stream, and `run()` has already stopped the `RunStatePublisher` by this point. Only happens when `run()` executes on the main thread - the same guard the `SIGTERM` registration above uses - so the three `telemetry_engine/demo_*_run.py` callers (`asyncio.to_thread()`) keep returning promptly rather than hanging forever.

An operator who just closes the browser tab instead of using any of the above sends this process nothing at all - there's no persistent connection, only polling - so the lingering process (and its dashboard port) would otherwise sit there indefinitely, silently costing the *next* test its own dashboard (its bind would just fail). `spawn_operator_dashboard()` calls `reclaim_stale_dashboard()` first to guard against exactly that: if the fixed dashboard port is still held, it's necessarily the previous test lingering (only one test/dashboard is ever up at a time on this test stand), so it reads that test's `test_id` from a small lock file the dashboard writes on successful bind, leaves it the same stop marker `stop_test.py` would (not a raw kill), and waits a few seconds for the port to free before the new dashboard binds - giving up gracefully (no dashboard, same as any other bind failure) if the old process doesn't free it in time.

**Running a test case.** `testcases/registry.py`'s `REGISTERED_TESTS` maps a `"<dut>.<test>"` key to a factory with a uniform `(test_id, use_mock)` call signature, regardless of whether the underlying `TestCase`'s own constructor accepts `use_mock` at all (`example_dut`'s tests don't, since that DUT has no real backend to choose between) - the factory itself absorbs that difference, not whoever calls it. A deliberate manual list - a single file every test author appends one line to, rather than introspection/auto-discovery magic. (It used to mirror `REGISTERED_RULEBOOKS` in `telemetry_engine/main.py`, which no longer exists: the engine stopped evaluating Rulebooks, and that hand-maintained list drifting out of sync was one of the reasons why - see Asimov.) `tools/run_test.py` is the generic entry point: `python -m tools.run_test --test <key> [--mock]` looks up the factory, constructs the test case, calls `.run()`. Replaces one-off runner scripts per test case; `demo_testcase_run.py`/`demo_ydrive_test_run.py` still exist alongside it for their own distinct purpose (proving the Telemetry Publisher's tagging plumbing works, complete with a frame-printing thread), not for operationally running a test case.

A deliberate stop surfaces out of `.run()` as `StopRequested`/`SystemExit`, since `run()` re-raises it after a clean teardown purely so a caller can tell a stop happened - `run_test.py` catches that pair specifically and reports it as a plain log line with a clean exit, rather than letting what was actually a successful, intentional stop print a traceback and exit code 1.

**Stopwatch** (`testcases/utils.py`): a small wall-clock elapsed-time helper (`start()`/`elapsed_s()`/`expired`) so a test's own sequencing logic (how long has this test run, how long since the last state change) reads in plain seconds instead of doing arithmetic on raw telemetry frame timestamps. Also directly iterable (`__iter__`, paced by its own `wait()`/`POLL_INTERVAL_S`), so `for _ in stopwatch:` is a fully self-pacing wait loop - no `.expired` check or sleep call for a test step to remember. Deliberately *not* used for a Rulebook's `persistence_s` debounce timing, which stays tied to the data's own timestamp (`frame.t`) rather than wall-clock time — see Asimov below. On a single test stand this is one shared system clock either way; the distinction matters if hardware driver and testcase execution processes ever run on different machines, where `frame.t` (stamped by whichever process owns the device) is the one value that's actually shared across the pipeline (the driver's own stream, storage, evaluation) and safe to correlate on - a `Stopwatch` reading in the test case's own process is not persisted anywhere and never needs to be.

**Client-side components**, used across the phases above - a test case that needs more than one device holds one HW command client and one telemetry client per device, each just pointed at a different device's endpoints, per the generic wire protocol:

- **HW command client** — talks to a hardware driver's command server (its universal core - `connect`/`disconnect`/`get_status`/`list_actions` - plus whatever device-specific actions that device supports via `execute()`); the generic `CommandClient` lives in `hardware/clients/`, but named convenience wrappers (e.g. `DutCommandClient`) live alongside each device's own backend in `hardware/mock_<device>/mock_<device>_command_client.py`, not in `hardware/clients/` - only the truly device-agnostic client code lives there.
- **Telemetry client** — subscribes to a hardware driver's telemetry server. Test steps never hold one directly today (see MainExecution above) - `ExampleDut` owns two: one handed to `LiveRulebookRunner`'s background thread for continuous evaluation, and a separate dedicated one for `get_channels()`'s synchronous point-reads, kept apart since a ZeroMQ socket isn't safe to read from two threads at once.
- **Run-state publisher** (`state_publisher.py`'s `RunStatePublisher`) — runs as a background thread for the whole life of the run, constructed in `TestCase.__init__` and started by `run()` before PreTestSetup, stopped after PostTestTeardown. It publishes one small `RunStateFrame` every `STATE_PUBLISH_INTERVAL_S` (20 Hz) carrying the run's identity (`test_id` random per run, `test_name` stable per test *type*), the devices this run claims, and every value the test has published via `set_state(name, value)` (e.g. `current_step`, `test_status`, `{bound_label}_status`).

  **It does not touch telemetry.** It used to: an earlier design had it subscribe to one device's raw stream, merge test context into every frame, and republish the lot - which meant every frame travelled through this process a second time, and meant only that one subscribed device could ever be attributed to a run. The engine now subscribes to each driver directly and merges this state into the rows it writes, so the relay hop is gone: a few hundred bytes at 20 Hz instead of megabytes a minute, and a test with any number of devices needs no extra wiring.

  Publishing is unconditional rather than change-triggered, which makes one mechanism do three jobs: propagate a change within one tick, keep the run alive in the engine's view, and heal ZeroMQ's slow-joiner drop. Construction is separate from starting so that PreTestSetup can seed state and hand the publisher to the evaluator without depending on `run()` having been called first - and so state set before publishing begins rides on the very first frame. Everything, including the `@step` decorator and step bodies, calls `test.set_state(...)` rather than touching the publisher.

### Asimov — the Rulebook evaluation framework (`testcases/asimov/`)

Named for Asimov's Three Laws of Robotics - the classic "rules governing robot behavior" reference. Holds the shape test authors use to define channel checks, and the shared logic that evaluates them over time:

- **`Bound`** (`rulebook.py`) — one channel check: `channel`, up to three optional constraints - `upper`, `lower`, `expected` - ANDed together (violated if the channel is above `upper`, below `lower`, or not exactly `expected`; any combination may be set), an optional `gate_channel`/`gate_value` (only evaluated when another channel - hardware or test-case-published state - has a specific value), an optional `persistence_s` (debounce: the raw condition must hold continuously for this many seconds before the bound is considered violated), and `fatal`/`event_name`, which only matter to a *live* evaluator (post-hoc evaluation ignores them, since it has no live test to abort or hardware event to fire). `Bound.evaluate(channels)` is a pure, stateless, instantaneous check - `None` if the bound doesn't apply this frame (gate not met, channel absent), else `True`/`False`. All three constraints compare only against fixed values today - see the open decision on comparing a channel against another live channel's value.
- **`Rulebook`** — a named collection of `Bound`s for one test type (`Rulebook.test_name`, matched against `TestCase.TEST_NAME`). Multiple Rulebooks can be registered for the same `test_name`.
- **`RulebookEvaluator`** — tracks per-bound violated/cleared state (and, when `persistence_s` is set, the debounce timer) across repeated `evaluate(channels, t)` calls against one ongoing stream of channel snapshots, emitting a `BoundTransition` only when a bound's state actually changes (not a firehose of one row per frame). Debounce is asymmetric and non-cumulative by design: **clearing is immediate** regardless of `persistence_s`, and **any gap resets the "how long has this been violated" clock to zero** - it doesn't pause and resume. This is the one piece of shared logic used *both* ways:
  - **Live**, via `LiveRulebookRunner` (`live_rulebook_runner.py`) - a test case constructs one with its own Rulebook(s) and the run's `RunStatePublisher`, then `start()`s it against a telemetry client; it runs its own background thread, and on each frame it evaluates the **union of that device's channels and the test's published state** (read in-process from the publisher, which is what lets a `Bound` gate on a published flag - the frames it consumes are a device's raw stream and carry no test state), publishes a per-bound live status channel (`f"{bound_label}_status"`, `"PASS"`/`"FAIL"`) and a recomputed aggregate `test_status`, fires `trigger_event` for any transition with an `event_name`, and raises `FatalBoundViolation` on a fatal breach - which stops this runner's own background thread (see `_run()`), not MainExecution's own thread (see the open decision on whether that's sufficient). This is the *only* place a bound violation can affect the running test at all today - per the "no feedback loop" principle.
  - **Offline replay**, via `telemetry_engine/replay.py`. Reads stored telemetry back off disk and runs the same `RulebookEvaluator` over it. Can never influence a running or already-finished test. (`evaluation.py`'s `Evaluator`, a per-`test_id` multiplexer over the same logic, was deleted: it had no callers anywhere and its only input type - the tagged frame - no longer exists.)

    This used to run *online*, inside the engine, over the frames the test process relayed to it - a second evaluator over the same bounds, and it was removed. Three reasons, in increasing order of seriousness: it read a copy one hop further downstream than the live runner and therefore lossier, so its `persistence_s` debounce could legitimately reach a different conclusion about the same run; it depended on a hand-maintained `REGISTERED_RULEBOOKS` list that **had already drifted** (`YDRIVE_RULEBOOK` was never added, so both real-hardware test cases silently produced an empty violations file); and it meant two independent answers existed to "did this run pass", only one of which - the live one - had actually gated the run. Pass/fail now has exactly one author. What post-hoc evaluation is genuinely good for is offline: replaying a stored run to ask whether *different* bounds would have caught something, and replaying with the *same* bounds to confirm the stored record explains its own verdict. Both are what `replay.py` does.

### 5. Telemetry engine process

`telemetry_engine/` — aggregator, storage, and per-run bookkeeping are sub-components of this one process, not separate OS processes; they communicate in-process, not over another wire hop. It has exactly three jobs: record telemetry, stamp each run's verdict with completeness stats, and advertise that it's recording. It deliberately does **not** evaluate Rulebooks — see Evaluation below.

- **Telemetry aggregator** (`aggregator.py`) subscribes to **every device** in `protocol/wire.py`'s `TELEMETRY_ENDPOINTS` - one socket each, plus one for the testcase process's run-state stream - and multiplexes them into a single in-process feed (an async generator) for the engine to consume. One socket per device rather than one socket connected to many endpoints: a single SUB socket would deliver all of their frames with less code, but then a silent stream is only detectable as "nothing at all is arriving", and per-socket pumps keep *which device went quiet* answerable. It does no correlation or joining; the engine decides where each frame belongs by asking the run recorder. The aggregator stays a dumb multiplexer, same spirit as the telemetry server staying "fast and dumb on purpose." It also exposes `devices`, which the engine publishes on its heartbeat so a test can confirm its declared devices are actually covered before it starts.
- **Storage** (`storage.py`, `wide_csv_storage.py`) — one minimal interface (`TelemetryStorage`, only `write()`/`close()`), mirroring `HardwareBackend`'s pattern: the rest of the system depends only on the interface, never a concrete store, so a real time-series database can replace the CSV implementation later without touching the aggregator or `main.py`. `WideCsvTelemetryStorage` is the only implementation today, and it fans one merged stream out across many files - see The per-run result record below for the layout. There is no longer a second `ResultStorage` interface for pass/fail data: a run's pass/fail *is* its verdict record, written by the test process itself.
  - **Writes are decoupled from socket reads.** `main.py` pushes frames onto a bounded queue drained by a dedicated writer task, rather than awaiting a write per frame with a flush per row (which at ~4,500 rows/s was the likeliest source of a stall, backpressuring straight into the SUB socket). A frame dropped because that queue is full is *counted*, per run, and reported in the verdict's `completeness` - distinctly from frames lost in transit, since the two have different fixes.
- **Run tracking and per-run bookkeeping** (`run_recorder.py`) — learns which run is open from the run-state stream, and answers the one routing question the engine asks per frame: `route(device)` returns the open run's `test_id` and the state to merge into its rows, or `None` for the continuous per-session record. The rule has no gaps and no duplication - exactly one destination per frame:

  | frame from device D | destination |
  |---|---|
  | run open, D declared by it | `runs/<test_id>/D/telemetry.csv`, state merged |
  | run open, D not declared | `raw/D/telemetry_<session>.csv` |
  | no run open | `raw/D/telemetry_<session>.csv` |

  It accounts every attributed frame against its run (per device, since `seq` is assigned by each driver independently and a shared counter would invent gaps whenever two devices interleave). When the run-state stream has been quiet for `DEFAULT_STALENESS_S` (5 s, a hundred missed ticks), it amends that run's `verdict.json` with the completeness stats only the engine can produce, closes that run's telemetry files, and - if no `verdict.json` exists at all - synthesizes a `lifecycle=CRASHED` verdict, so a test process killed outright still leaves a record. A *different* `test_id` appearing finalizes the previous run immediately rather than waiting out staleness: two runs never overlap on one stand.

  There is deliberately no start or end marker on the state stream. A start marker would protect nothing, because the run is announced before any driver exists, so there are no frames to misroute. An end marker would be worse than useless: the verdict file already distinguishes a clean end from a crash, more reliably since it is written atomically before teardown, and finalizing the instant a marker arrived would truncate frames still in the engine's write queue.
- **Evaluation** — deliberately not part of the recording path. `evaluation.py`'s `Evaluator` and `replay.py` exist for *offline* replay against stored telemetry; nothing here evaluates a live stream. See Asimov below for why the online post-hoc evaluator was removed.
- **Liveness heartbeat** (`protocol/heartbeat.py`) — refreshed each tick while recording, and cleared on clean shutdown. This is what a test checks before starting and while running; see Recording is a precondition for the test below.

This process remains a **terminal sink for evaluation results** — no verdict, violation, or telemetry value computed here ever flows back to influence a running test. Implications:

- Results here are for reporting, dashboards, and offline analysis, not for real-time test sequencing decisions.
- Any check that needs to influence the live test sequence (e.g., "abort if channel X exceeds Y") must be implemented inside the testcase execution process (via `LiveRulebookRunner`, using the test case's own telemetry client), not by waiting on a result from this process.
- The one thing that *does* cross back is the engine's own liveness, and only its liveness - a heartbeat file carrying a pid, an output directory and a timestamp, never a result. See the refined principle under Design principles.

## Declared channels must exist

Every channel a `channels.py` declares must resolve on the device at runtime, or the run fails at setup with a `MissingChannelError` **naming each missing channel and its attribute path**. A declared-but-absent channel is never tolerated: the point of declaring one is that someone intends to make decisions from it later.

**The hole this closed.** A backend that catches `AttributeError` and substitutes `None` leaves the channel key present in every frame, so `TelemetryClient.verify_channels()` (which compares expected names against a frame's keys) finds nothing missing and setup reports healthy - while that column stays empty for the whole run. Eleven declared ODrive channels behaved this way on the first real-hardware run. Worse, a `Bound` on such a channel compared `None` against a numeric limit, raising `TypeError` *inside* the live evaluation thread: that killed the thread, left `fatal_violation` unset, and the test ran to completion with **no safety monitoring**, reporting healthy throughout.

**Why emptiness can't be the signal.** "Not present" and "no value right now" are different facts, and only the driver process can tell them apart. On that run 13 columns were always empty but only 11 channels were structurally absent - the other two were test-published state channels that exist fine and that this particular test never set. An assertion driven by empty values would condemn those.

**How it works.** A real backend probes every declared path once at `connect()`, walking intermediates so a missing parent is caught as cleanly as a missing leaf, and raises listing everything that failed. Setters and methods are probed with `hasattr` on the resolved parent - never by writing or calling, since a health check must not have side effects on hardware. That also closes the same hole on the command side, which `verify_actions()` cannot catch: it only asks whether `list_actions()` returns a name, and that list is table-driven rather than probed (three declared ODrive setters pointed at non-existent firmware paths and would have failed at set time). `_read_all_channels()` no longer catches `AttributeError` at all - if absence somehow appears mid-run it propagates, and `runner.py` shuts the driver down, which is correct: the device's attribute graph changed underneath us.

**Defence in depth.** `Bound.evaluate()` raises `UnevaluableBoundError` rather than `TypeError` for a value it can't compare, and `LiveRulebookRunner` treats that exactly as a silent telemetry stream: fatal. A bound that cannot be evaluated is not a bound that passed, so `bounds_result` becomes `NOT_EVALUATED`, never `PASS`. An `expected`-only bound needs no ordering and still accepts any type.

**Trade-off accepted.** A declared list pruned to what a board actually has describes *that board configuration*, not the device's full documented API. A board with extra hardware won't record those channels until they're re-added; a board with less fails at setup, loudly, which is the point.

## The per-run result record

Every test run produces exactly one directory: one authoritative verdict plus the telemetry backing it. This is the durable contract a real report database eventually ingests, so it's specified here rather than left implicit in the code.

```
<output_dir>/
  runs/<test_id>/
    verdict.json              how the run ended, whether the DUT behaved,
                              every bound transition, completeness, metadata
    <device>/telemetry.csv    wide: one row per frame, one column per channel
  raw/<device>/telemetry_<session>.csv
```

`protocol/paths.py` owns the layout and both processes derive their paths from it. The test process never hardcodes `<output_dir>` - it reads the engine's actual one from the heartbeat, so the two can't disagree.

**Two orthogonal outcome fields, not one enum** (`protocol/verdict.py`). `lifecycle` is how the run ended (`COMPLETED`/`STOPPED`/`ERRORED`/`CRASHED`); `bounds_result` is whether the DUT stayed inside its bounds (`PASS`/`FAIL`/`NOT_EVALUATED`). A derived `outcome` (`"STOPPED/PASS"`) exists for logs and the dashboard, and is never the thing to query. One enum can't express a test that runs until an operator stops it and passes: it must file that as either not-a-failure (hiding any violations from a query) or an outright failure. Two small closed enums also map to two indexed database columns.

- `NOT_EVALUATED` is a distinct third state on purpose, derived from whether the runner evaluated ≥1 frame. A base test case may leave `runner.start()` to its subclasses, so "constructed but never started" is reachable, and a run with *zero* monitoring must not record identically to a clean one. It also covers a bound that became unevaluable mid-run.
- A fatal-bound abort records `lifecycle=ERRORED` (an exception did propagate out of `main_execution`) with `bounds_result=FAIL` and `any_fatal=true`. That a *bound* caused it is recorded by those fields, not by overloading `lifecycle`.

**Any violation fails the run.** `bounds_result` is `FAIL` if any bound violated at any point, even if it later cleared, `fatal` or not. `fatal` governs one thing only: whether the test aborts. So a `Bound` is *always* a pass/fail criterion and can never be a purely informational monitor - anything watched but not judged must be something else, e.g. a published state channel.

**The full transition timeline lives in the verdict.** `violations` is every violate and clear in order, each carrying the frame's own `seq`/`t` so it aligns with - and replays against - the stored telemetry. Deliberately not a separate store: a timeline written by a different process on a different lifecycle is how a verdict ends up referencing violations nobody recorded. Ports as one row plus one child table. Unaddressed limit: nothing caps its length, so a flapping *non-fatal* bound on an indefinite run grows the record without bound (`persistence_s` bounds the rate, and fatal bounds self-limit since the first violation aborts).

**Who writes what.** The test process writes `verdict.json` atomically into the run directory *before* `post_test_teardown()` - everything it records is already determined, the record exists before any teardown delay, and `result_metadata()` can still read live hardware. The engine only adds `completeness`, once that run's stream has gone quiet. There is no spool directory and no settle window: the verdict's existence is the whole check, so a late verdict simply wins.

**Telemetry is wide, one file per device.** Columns are fixed from the union of the first `HEADER_SAMPLE_FRAMES` frames, since a run-attributed row carries test-published state channels that appear only once something sets them. That window is about four seconds at the real device's rate, so a state channel first published later than that is absent from the file apart from one log line - which is why every state channel is seeded with a default during setup. Wide rather than long/tidy because the "one point per tag/field/timestamp" shape a TSDB wants is a loop inside a `TelemetryStorage.write()` implementation, not a property of the interim file - and long repeated the `test_id` and channel name per value (~15x larger, measured). Per *device* because devices differ in rate and number `seq` independently, so one table per run would have to interpolate or pad; aligning them stays a deliberate query on `t`.

- A channel appearing after the header is fixed is logged once and dropped; one missing from a frame is an empty cell. Both stay visible rather than silent.
- Files open in **append** mode, so an engine restart mid-run keeps adding to the same file.
- The per-session files stay outside `runs/` because they hold exactly the frames that belong to no run: everything a device published while no test claimed it, including the window after a test process died and its state stream went quiet. Recover an unattributed slice by time range.

**Completeness is measured, not assumed.** The transport is best-effort by design - PUB/SUB drops under backpressure, and a subscriber attaching mid-stream misses what preceded it - and no HWM makes that impossible. So every run records what actually arrived: `frame_count`, `seq_gap_count` (lost in transit) and `dropped_frames` (received but unwritable), plus a per-device breakdown. The two loss counters stay separate because they have different fixes. The acquisition record *of record* remains the DAQ in the hard-real-time tier; this path is supervisory. `completeness: null` is itself meaningful - the engine never finalized the run, so the record is partial.

- HWMs are set explicitly and expressed in **seconds of buffer** per device (`hwm_for_interval`), since a raw frame count means very different things at different rates. Deliberately modest: with writes decoupled from socket reads, a deep queue only converts a slow writer into invisible latency, where a shallow one surfaces it as a counted drop - and it must stay small enough for many devices to each hold one.

**Volume, measured.** ~35 MB/hour, ~5.8 GB/week for a ~117-channel device at ~12.6 Hz. An indefinite run still grows without bound, so disk headroom is an operational concern the format doesn't solve. Two earlier estimates were wrong by ~6x: the real device achieves ~12.6 Hz rather than the 20 Hz its `SAMPLE_INTERVAL_S` implies (it's a sleep *between* frames, and the per-channel USB round-trips add ~29 ms), and the wide format's saving is ~15x rather than the ~4x first claimed.

## Operator tooling

`tools/` holds the operator-facing entry points - `run_test.py`, `stop_test.py`, and `operator_dashboard.py` (see Testcase execution process above for all three) alongside `manual_gui.py`, described here. None of these are one of the five processes above, and nothing in the process architecture depends on any of them existing.

`tools/operator_dashboard.py` is the automatically-spawned status page every test case shows (see "Operator status page" above) - a plain stdlib `http.server`, not a new web-framework dependency, since its whole surface is three endpoints: the page itself, a JSON status poll, and the stop action. Status/error are pushed into it explicitly from `TestCase.run()` rather than the page polling the test case itself - that's what lets it correctly show an error for a failure that happens before any Rulebook runner even exists (e.g. a `PreTestSetup` crash), and it needs zero device- or DUT-specific knowledge, same as `manual_gui.py`. Deliberately has no command-sending capability at all, unlike `manual_gui.py` - it's shown for *every* test, including fully automated ones, and letting an operator inject arbitrary commands into an already-running automated sequence could interfere with its own control logic; a read-only status view plus a graceful stop is the only interaction that's safe to expose everywhere.

`tools/manual_gui.py` is a Tkinter GUI that connects to already-running processes as just another client. It has no device-specific knowledge at all: telemetry channels are discovered live from whatever keys show up in an incoming frame (never imported from any device's `channels.py`), and a command device's available actions are discovered live via `list_actions()` - so the same tool works unmodified against any current or future testcase, including hardware this repo doesn't support yet.

Telemetry and commands are both added by endpoint during a session (an "Add" field + button for each, mirroring each other), rather than the GUI being told up front which single device to watch/command - this matters once more than one device is in play, since a flat/shared representation (one merged stream, a deduplicated set of command action names) has no way to disambiguate which device a channel or action actually belongs to. The run-state stream (`DEFAULT_RUN_STATE_ENDPOINT`) is subscribed by default for test-level context (`test_id`/`test_name`, Rulebook bound-status, `current_step`) - it's genuinely singular, since only one test case ever runs at a time on this stand, and it carries only state, no hardware channels - but it's just one more entry among however many raw per-device telemetry subscriptions get added, editable/reconnectable the same way.

A checked telemetry channel plots live on a matplotlib graph embedded via `FigureCanvasTkAgg` (dual independently-auto-scaling y-axes, manually assigned per channel - no automatic/heuristic grouping; a rolling 10-minute buffer regardless of which time window - 10s/30s/1min/10min - is currently displayed, so switching window size is instant; pausing only freezes the redraw, buffering continues underneath, so nothing recorded is lost). A checked command channel gets an editable JSON params field (e.g. `{"value": 1.5}`) plus a Send button - JSON, not a bare value, because the wire protocol has no way to discover an action's parameter names/count (`list_actions()` returns names only), so there's no generic way to know `set_position` wants `value=` while `set_axis_state` wants `state=` and `move_incremental` wants two params, without hardcoding per-action knowledge this tool is built to avoid. "Value" for a command channel is always the last value *sent from this GUI*, never a live hardware readback - there's no generic way to read one back either, since reading is the telemetry stream's job, not the command server's. A send is guarded against a second concurrent send to the same channel - `CommandClient`'s REQ socket isn't safe for two threads to use at once, and each Send spawns its own background thread so a slow device can't freeze the whole GUI.

`ManualTest` (see Testcase execution process above) is what this tool was originally built for: a test case with no test sequence of its own, whose only job is keeping a device's driver process and command/telemetry endpoints alive for this GUI to connect to.

## Design principles

- **Single owner of hardware.** Exactly one process talks to a given device. Everything else goes through its command/telemetry interfaces. Adding a device means adding a process, never adding a second connection into an existing one.
- **Testbed vs. DUT are separate concerns.** The physical fixture/instrument setup (`testbeds/`) is managed independently from the product being tested (the DUT abstraction under `testcases/<dut>/dut/`) - a testbed never issues DUT commands, and the DUT abstraction never manages instrument processes.
- **Single source of truth for channel checks.** A `Bound`'s definition (value, comparison, fatal/event_name, persistence) is written once, in a `Rulebook`, and used both for live in-test control (`LiveRulebookRunner`) and offline replay (`telemetry_engine/replay.py`) - not duplicated as two independently-maintained threshold definitions.
- **Shared evaluation logic, not duplicated bookkeeping.** `RulebookEvaluator`'s transition-tracking (and debounce) logic is written once, in `testcases/asimov/rulebook.py`, and reused by both the live and post-hoc paths - only who calls it, how many instances exist, and what they do with the result differs.
- **Debounce is asymmetric and intentional.** `persistence_s` only delays a bound *becoming* violated; clearing is always immediate, and any interruption resets the debounce clock rather than accumulating - matching how a real alarm/limit-check debounce is expected to behave.
- **Test sequencing timing is decoupled from telemetry data timestamps.** A test's own control flow (`Stopwatch`) uses wall-clock time in its own process; a Rulebook's `persistence_s` uses the data's own timestamp (`frame.t`) - these serve different purposes and are not interchangeable.
- **Separation of raw ingest from evaluation.** The telemetry server/publisher path never does evaluation logic; that's isolated to the telemetry engine so it can change independently.
- **Telemetry is relayed by nobody.** Every frame reaches the engine straight from the driver that produced it; the testcase process publishes only its own small state stream. So a bug or crash in the testcase execution process costs that window's *test context*, never its data - and because there is only ever one copy of a frame, nothing is written twice to buy that. This replaced a design where the test process relayed every frame, which both doubled the write volume and limited a run to the single device the relay happened to subscribe to.
- **Hard real-time stays in hardware.** No software process in this architecture is on the safety-critical path.
- **No feedback loop of evaluation results from the telemetry engine to command.** Keeps it a simple downstream consumer; live decision-making logic lives entirely in the testcase execution process. Refined wording, and the distinction is load-bearing: what this forbids is a *result* computed downstream influencing a running test - a violation, a verdict, a derived value - so that all live safety logic stays in the one process holding the hardware. It does not forbid the test noticing *infrastructure* state. `check_recording_alive()` reads a heartbeat carrying a pid, a directory and a timestamp, pulled by the test from the filesystem, structurally identical to `check_stop_requested()` - which is already an external process influencing a test through a marker file, and which this document endorses.
- **One author of pass/fail.** A run's outcome is decided by exactly one evaluator - the live `LiveRulebookRunner`, in the test process - and recorded verbatim in the verdict. Nothing downstream recomputes it. Two evaluators over the same `Bound` definitions could disagree about the same run, and only the live one ever actually gated it.
- **`fatal` governs abort, not pass/fail.** Any bound violation fails the run; `fatal` decides only whether the test stops immediately. So a `Bound` is always a pass/fail criterion, never an informational monitor.
- **Orthogonal outcomes stay orthogonal.** How a run ended and whether the DUT behaved are separate fields, because a run can end deliberately and still be a success, or complete normally and still have failed.
- **Record best-effort, but measure the gaps.** The telemetry path is supervisory, not the acquisition record of legal standing (that's the DAQ, in the hard-real-time tier). Rather than claim a completeness the transport can't deliver, every run records what actually arrived, with frames lost in transit counted separately from frames the engine couldn't write.
- **A test that can't be recorded doesn't run.** Recording liveness is a precondition, checked before start and polled throughout - see Recording is a precondition for the test.
- **One home for cross-process contracts.** Anything two processes must agree on lives in `protocol/`; no process imports another's internals.
- **One façade per DUT.** `ExampleDut` (and any future DUT abstraction) is the single object test-authored code touches for that DUT - every command/telemetry channel gets its own named `get_<channel>()`/`set_<channel>()` method, even where that's a thin forward to the underlying command/telemetry client. Test steps never reach into `.command`/`.telemetry` directly, and never touch a telemetry frame, a channels dict, or evaluation at all - see MainExecution above.
- **Positively confirm channels exist, don't assume.** Each backend declares its own `TELEMETRY_CHANNELS`/`COMMAND_CHANNELS` (`hardware/mock_<device>/mock_channels.py`), and the DUT abstraction checks them against the *live* driver process at `start()` (`verify_channels()`/`verify_actions()`, raising `MissingChannelError`), rather than trusting a hand-maintained list that could silently drift from what the backend actually implements.

## Timeout watchdogs (cross-process hang protection)

Every blocking cross-process receive is bounded, so a dead or hung peer — a crashed driver process, a stopped publisher, a wedged real-device call — can never hang a test forever; the failure surfaces as a prompt, typed exception instead. This is an architectural property, not a per-call afterthought: the two clients that every test depends on both carry their own watchdog.

- **Telemetry client staleness deadline.** `TelemetryClient` (`hardware/clients/telemetry_client.py`) takes a `timeout_s` (default 5s); `frames()` polls with that deadline and raises `TelemetryTimeout` if no frame arrives within it of the previous one (or of the call, for the first). This is the most-consumed hang point in the framework — the `LiveRulebookRunner` evaluation loop, `verify_channels()` during setup, and `get_pos_estimate()`/`get_vel_estimate()` inside a closed-loop move all block here. The deadline is one poll per frame, so a healthy stream (frames far more frequent than `timeout_s`) is never affected; it fires only on a genuinely silent stream. `TelemetryTimeout` subclasses builtin `TimeoutError`, so existing `except TimeoutError` handlers still catch it — and it closes a real gap where `move_to`'s own arrival deadline was checked only *between* frames and so could never fire if the stream died mid-move.
- **Command client, both halves bounded.** `CommandClient` (`hardware/clients/command_client.py`) sets both `RCVTIMEO` and `SNDTIMEO` to `timeout_ms` (default 5s) and raises `CommandTimeout` (a `CommandClientError` subclass) on either. It deliberately does *not* rebuild the `REQ` socket on timeout: a `REQ` socket's strict send→recv alternation leaves a timed-out socket broken, and the only "recovery" — recreate and resend — could double-apply a stateful command (a relative `move_incremental`, a `set_position` on a real motor). Instead it marks itself broken; every later `execute()` raises a clear `CommandClientError` telling the caller to reconstruct the client, rather than leaking the cryptic zmq EFSM error the broken socket would otherwise throw. A command timeout is effectively fatal to that client instance by design — the caller aborts and tears down.
- **A silent telemetry stream is fatal to the test.** `LiveRulebookRunner` treats a `TelemetryTimeout` from its loop exactly like a fatal bound violation: it stores it on `fatal_violation`, so the test's existing `check_fatal_violation()` poll (in `wait_for()`/`@step`) raises and drives a clean teardown. Losing live telemetry mid-test means losing safety monitoring while the hardware may still be moving, so the test stops rather than running blind. A silent stream *during* an already-in-progress stop is not counted as a failure.
- **The aggregator stays up instead of failing.** `telemetry_engine`'s `Aggregator` is a long-lived service, not a test, so its stream pumps do the opposite of the clients: on a silent stream past the same deadline they log a staleness warning once and keep looping, recovering on their own when frames resume, rather than raising. Different behavior, deliberately — a service should stay observable, not die on a gap.
- **The command server is deliberately left unbounded.** No `asyncio.wait_for` guards `command_server.py`'s backend calls, because device operations have no sane fixed ceiling (calibration/homing legitimately run for many seconds) and a naive server-side timeout would kill real work. The client watchdog is the real protection: one client per driver, one test at a time, so a wedged backend call is already backstopped by the client timing out, the test aborting, and the whole driver process being terminated — at which point the stalled server loop dies with it.

## Verification

Two complementary layers:

- **`tests/` (pytest, `uv run pytest`)** — 72 fast, hardware-free unit tests over the pure logic: the verdict record's round-trip and atomic write/amend (the database-port contract), the `lifecycle` × `bounds_result` derivation including `NOT_EVALUATED` and the false-pass case, `RunSummary`'s timeline and the any-violation-fails rule, wide-CSV header formation/routing/append, engine-side completeness and `CRASHED` synthesis, replay equivalence, heartbeat/abort paths, and declared-channel presence. The project's first automated suite; before it, verification was entirely manual.
- **`demo_*.py` scripts** — nine runnable end-to-end demos, for what needs real processes, sockets and subprocess lifecycles. `telemetry_engine/demo_evaluation_run.py` is the replay demo: it records a shortened run, then replays the stored telemetry and checks the timeline against the verdict.

**Confirmed against real hardware.** A `ManualTest` run against a real ODrive Pro (fw 0.6.11) recorded `STOPPED/PASS` with 0 seq gaps and 0 writer drops, and replay reproduced the timeline exactly. `ManualTest` was chosen deliberately: it exercises the full record pipeline at real USB rates while leaving the axis `IDLE`, so nothing moves. That run produced the measured rate and volume figures above, corrected both by ~6x, and surfaced the absent-channel hole (see Declared channels must exist).

**Still needs a human.** Neither abort path (engine killed mid-run, test process `SIGKILL`ed) has an automated equivalent - both were provoked by hand, and both turned up real bugs when first run. And no *moving* real-hardware run has gone through the new pipeline yet, which would additionally exercise bound evaluation under real load.

## Resolved implementation decisions

- **The testcase process no longer relays telemetry; the engine attributes frames itself.** Previously a `TelemetryPublisher` subscribed to one device's raw stream, merged test context into every frame, and republished the lot as a "tagged" stream that the engine recorded. That had three problems: every frame of every device travelled through the test process a second time; only the one subscribed device could ever be attributed to a run, so a multi-device test recorded exactly one of its devices; and the engine wrote both the raw and tagged copies of the same frame, roughly doubling storage wherever the raw path was actually wired up. It is replaced by a `RunStatePublisher` that broadcasts only the run's identity, its declared devices, and its published state (20 Hz, a few hundred bytes), while the engine subscribes to every device directly and routes each frame itself - run directory if the open run declared that device, per-session record otherwise, exactly one destination per frame. `TaggedTelemetryFrame` is gone from `protocol/wire.py`. The clinching argument was that of the four consumers of the old tagged stream, three (`stop_test.py`, `operator_dashboard.py`, `manual_gui.py`) only ever read *state* out of it; the telemetry payload had exactly one consumer, the engine, which was already receiving the same frames on the raw path.
- **A test declares the devices it claims, and each owner declares its own.** A testbed declares the instrument devices whose driver processes it starts; a DUT façade declares the DUT's. The base test case unions them into `TestCase.DEVICES`, so neither owner learns about the other and the testbed/DUT split stays intact. Verified end-to-end: a `CycleDutPositionTest` run now records the power supply into its run directory, which the relay design discarded entirely.
- **A run that declares a device the engine isn't recording fails before setup.** The engine publishes its subscribed device roster on the heartbeat; `require_recording_started()` checks the run's `DEVICES` against it and raises `DeviceNotRecorded`, naming the missing ones, before any hardware starts. Same principle as declared channels having to exist: a run directory quietly missing a device is not an acceptable outcome. A device roster is infrastructure state, like the `output_dir` the heartbeat already carries, not a result computed about the DUT - so this does not breach the no-feedback rule.
- **No start or end marker on the run-state stream.** Its existence says a run is open; its silence says the run is over; the verdict file distinguishes a clean end from a crash. A start marker would protect nothing (the run is announced before any driver exists), and an end marker would tempt the engine to finalize while frames were still queued.
- **Gating on published state works live, and an unresolvable gate is fatal.** The live evaluator consumes a device's *raw* stream, which carries no test state, so a `Bound` gating on a published flag could never fire - it was silently skipped on every frame while the run still reported `PASS`. The runner now evaluates the union of the device's channels and the publisher's state snapshot, read in-process. Separately, a `gate_channel` that exists nowhere raises `UnevaluableBoundError` rather than returning "doesn't apply", so a permanently-unevaluable bound can't masquerade as a passing one. A gate that *exists* and holds another value still just means the bound doesn't apply right now, which is the point of gating.
- **The run-state publisher is constructed in `__init__` and started by `run()`.** Building it in `run()` made `pre_test_setup()` silently dependent on call order - `set_state()` guarded on `None` and quietly did nothing - which is the failure mode this project refuses elsewhere. Construction opens no socket, so the split costs nothing and state set before publishing begins now rides the first frame.

- Wire protocol for command server/client: ZeroMQ REQ/REP. Wire protocol for telemetry server/client and telemetry publisher/aggregator: ZeroMQ PUB/SUB. The aggregator → storage/evaluation hop is not a wire protocol at all - they're sub-components of one process, connected in-process.
- Test case lifecycle: a custom three-phase model (PreTestSetup/MainExecution/PostTestTeardown), split into a reusable base case (`BaseExampleDutTest`, no test logic) and concrete subclasses (`CycleDutPositionTest`) - not a generic state machine or literal pytest test discovery.
- Hardware backend interface: a small universal core (`connect`/`disconnect`/`get_status`/`stream_samples`/`list_actions`) plus one generic `execute(action, **params)` for anything device-specific. Proven against three unrelated device types (DAQ, power supply, DUT - the last being a control loop, not just a readback) with zero changes to the command/telemetry server code. `list_actions()` was added later, alongside channel declaration below, so a client can positively confirm a backend's real command surface instead of trusting a static list.
- Testbed vs. DUT separation: `testbeds/<device_under_test>/` owns instrument processes (DAQ, power supply) only, including a ready-to-use command client for each (e.g. `testbed.power_supply`); `testcases/<dut>/dut/` owns the DUT's own driver process and command/control channel. Neither manages the other.
- Multi-device command control and defensive teardown: PreTestSetup/PostTestTeardown hold one client per device and set them up/tear them down independently; PostTestTeardown always runs unconditionally, and its individual steps run independently via `_teardown_step()`, which logs rather than raises.
- Storage interfaces: `TelemetryStorage` only (`write()`/`close()`), with wide per-device CSV as the interim implementation. `ResultStorage`/`CsvResultStorage`/`ViolationEvent` were **deleted**: a run's pass/fail is its verdict record now, authored by the test process, with the full transition timeline embedded. See The per-run result record.
- The per-run result record and its layout - see The per-run result record for the full specification. Verified end-to-end against both mock and real backends, including replay reproducing the recorded timeline.
- One online evaluator, not two: the engine's post-hoc `Evaluator` was unwired from the recording path and `evaluation.py`/`replay.py` are now offline-replay tools. See Asimov for the three reasons, one of which was an already-drifted `REGISTERED_RULEBOOKS` list silently producing empty violation files for both real-hardware test cases.
- Recording liveness as a test precondition (`protocol/heartbeat.py`) - see Recording is a precondition for the test. Both failure directions were provoked by hand: killing the engine mid-run aborted the test and tore down cleanly; `SIGKILL`ing the test left the engine to synthesize `CRASHED`. Two bugs surfaced doing so (the check firing during teardown, and the abort lingering forever unattended), both now covered by regression tests.
- `protocol/` as the one home for cross-process contracts, replacing `hardware/protocol.py` (31 files' imports rewritten - note a grep for the absolute import form undercounted this at 17, because everything inside `hardware/` used relative imports).
- `device` carried on the telemetry frame, set by the publishing driver rather than inferred from which endpoint a subscriber connected to - needed once more than one device streams into one test, since two can declare the same channel name. Per-device storage keys off it, and future per-device artifacts (status/error logs) follow the same convention.
- Explicit HWMs expressed in seconds of buffer per device, plus storage writes decoupled from socket reads via a bounded queue with counted drops and periodic (not per-row) flushing.
- First automated test suite (`tests/`, pytest, `uv run pytest`) - see Verification. New infrastructure for this project, which had relied entirely on runnable `demo_*.py` scripts; those remain for what genuinely needs real processes and sockets.
- Rulebook framework (Asimov): `Bound`/`Rulebook`/`RulebookEvaluator`/`BoundTransition` in `testcases/asimov/`, with `fatal`/`event_name`/`persistence_s` unifying what used to be two separate, duplicated threshold-definition mechanisms (a live-only `ChannelLimit` and a post-hoc-only `Bound`) into one. `LiveRulebookRunner` extracted separately as the live-side wiring (publish status, log, fire events, decide fatal), since that plumbing is identical for any test case using a Rulebook. A `Bound` checks one channel against up to three fixed-value constraints - `upper`/`lower`/`expected` - ANDed together; comparing against another *live* channel's value was tried (`Comparison.DEVIATES`) and deliberately dropped as premature generality with only one consumer (see open decisions). The one concrete case that needed it (`CycleDutPositionTest` checking position against a moving commanded target) now closed-loops in the test step itself instead, via `ExampleDut.get_position()` - see MainExecution above.
- Debounce (`persistence_s`): asymmetric (instant clear, delayed violate) and non-cumulative (any gap resets the clock) - deliberately, not a bug.
- Test sequencing timing: `Stopwatch` (plain wall-clock elapsed time, also directly iterable for self-pacing wait loops) for a test's own control flow, kept separate from `frame.t` (used only for Rulebook `persistence_s` debounce, which must stay tied to the data's own timestamp).
- Behaviour shared by every backend lives on `HardwareBackend`, not re-derived per device: the connected-state guard (`_require_connected`, previously an identical copy in all five backends, with `is_connected` overridable for backends whose connection is a handle rather than a flag), the `device` name and `sample_interval_s` (declared per backend class and read off it by `runner.run()`, instead of each device's `main.py` hand-passing both), and `to_jsonable()` for coercing device values onto the JSON wire. `runner.run()` is back to `(backend, command_endpoint, telemetry_endpoint)`, and the branch in `hardware/odrive/main.py` that picked between the mock's and the real backend's sample interval is gone, since each class declares its own. The obligation to confirm declared channels exist is stated in the ABC's `connect()` docstring rather than added as an abstract method with a single implementation.
- Declared channels must exist at runtime, or the run fails at setup naming each missing channel and its path - see Declared channels must exist. 14 declared ODrive channels were absent on the real board and have been pruned.
- Channel declaration and verification: each backend declares its own `TELEMETRY_CHANNELS`/`COMMAND_CHANNELS` (`hardware/mock_<device>/mock_channels.py`), and the DUT abstraction (`ExampleDut.start()`) positively confirms both against the live driver process (`TelemetryClient.verify_channels()`, `CommandClient.verify_actions()`), raising `MissingChannelError` immediately rather than a test discovering a gap later. Resolved and implemented for the DUT only so far - see Open implementation decisions for extending it to the DAQ/power supply.
- DUT abstraction shape: one façade (`ExampleDut`) with a named `get_<channel>()`/`set_<channel>()` method per command/telemetry channel, even where that's a thin forward to the underlying client - not a class that re-exposes its command/telemetry clients for callers to reach into directly.
- First real (non-simulated) device: `hardware/odrive/` holds `OdriveBackend` (real, official `odrive` PyPI package over USB, firmware 0.6.x / Pro-S1) alongside `MockOdriveBackend` (simulated), both implementing the exact same `HardwareBackend` interface with zero changes to the command/telemetry server code - confirming the generic framework holds against real hardware, not just further simulation. The `odrive` package import itself is deferred to inside `connect()` (not module load time), so the module - and `main.py --mock` - work without the package installed; only an actual USB connection attempt requires it. `connect()` itself only opens the USB link and confirms the device answers - it does **not** engage `CLOSED_LOOP_CONTROL`; a caller must call `set_axis_state("CLOSED_LOOP_CONTROL")` explicitly before commanding position/velocity/torque, the same way this framework never assumes a power supply's output should be on just because it's connected. `OdriveBackend(serial_number=...)` picks a specific board if more than one ODrive is attached (see the earlier "multiple ODrive controllers" discussion). This backend targets the common case for this test framework specifically: a single onboard-encoder (the Pro/S1's built-in magnetic encoder), non-ACIM (i.e. PMSM/BLDC), USB-connected axis - not ODrive's full generality (CAN transport, external incremental/hall/SPI/RS485 encoders, induction motors, sensorless operation are all out of scope, see the pruning bullet below).
- Curated ODrive channel surface, generated from one master table: the channel list was first deliberately expanded to cover ODrive's entire documented 0.6.x API (~450 telemetry + ~301 command channels) to prove the generation approach against the full surface, then pruned back to 99 telemetry + 71 command channels (~110/~74 until 14 declared-but-absent channels were removed - see Declared channels must exist). What was cut, by category: (a) one-time commissioning/calibration config nobody touches per-test (lock-in spin-up params, autotuning, harmonic/anticogging compensation, motor/resistance calibration settings); (b) internal control-loop diagnostics one level too deep to mean anything without also being a firmware developer (FOC/ACIM/sensorless-estimator internal state, per-phase ADC calibration coefficients, task-execution-time profiling); (c) hardware this framework doesn't use (CAN bus transport/config, step/dir GPIO interface, non-onboard encoder types - incremental/hall/SPI/RS485 - and the mechanical holding brake). See `odrive_channels.py`'s docstring for the short version; the discarded exhaustive version remains in git history if ever needed. Rather than hand-writing dozens of near-identical accessor methods, `odrive_backend.py` resolves every kept channel through a single `_TELEMETRY_PATHS`/`_SETTERS`/`_METHODS` table (channel name → real dotted attribute path) via a generic `_get_path`/`_set_path`/`_call_path` reflection walker; `odrive_command_client.py`'s named convenience methods and `mock_backend.py`'s per-channel defaults are generated from that same table, cross-validated in code so every declared channel has exactly one implementation and vice versa. `odrive_backend.py` also asserts this coverage match at import time (`_validate_channel_coverage()`) so future drift between the declared channel lists and the implementation tables fails loudly instead of silently. Every channel that survived the pruning pass is from the "core" set whose real attribute paths were individually cross-checked against ODrive's own 0.6.x fibre API reference - unlike the exhaustive version, there's no remaining unverified-but-plausible long tail.
- `OdriveBackend` connect-only verification against a real ODrive Pro over USB (`hardware.odrive.main`, no `--mock`): `odrive` made a hard dependency (`pyproject.toml`) now that real hardware is in active use, rather than the optional extra it started as. `connect()` found and connected to the physical device, and the declared command/telemetry channels round-tripped correctly (`verify_actions()`/`verify_channels()`). Eleven telemetry channels reported `None` with a "not present on this device" warning (brake resistor, some inverter/encoder sub-fields, charge/power totals), which was recorded here as "expected hardware-config-dependent absence, not a bug" - **that judgement was wrong and has been reversed**; see Declared channels must exist. `ManualTest` (see Testcase execution process) has also been run against this same real ODrive multiple times: connects, axis stays `IDLE`, live Rulebook evaluation runs, teardown (including a `SIGTERM` stop) completes cleanly. Closed-loop control (`set_axis_state("CLOSED_LOOP_CONTROL")` and beyond) has since been exercised and validated against real hardware - see the real-hardware motion bullet below.
- ODrive documentation research methodology and known caveats: paths were confirmed by fetching the raw HTML of ODrive's autogenerated fibre-type API reference (`docs.odriverobotics.com/v/latest/fibre_types/com_odriverobotics_ODrive.html`) and reading its "Expanded Path" field - generated directly from the firmware's own interface definition - as ground truth, rather than trusting prose documentation pages (which had real, confirmed inconsistencies with each other and with the autogenerated reference). Specific caveats worth remembering: (1) `axis0.motor.foc.Iq_measured`/`Id_measured` is the correct, confirmed path - a prose manual page's shorthand (`axis.foc.Iq_measured`, omitting `.motor`) is a documentation typo, not an alternate valid path; (2) the torque-constant formula is stated inconsistently across ODrive's own docs as either `8.27/Kv` or `8.23/Kv` - `motor_config_torque_constant` is just a plain settable value here, this codebase doesn't hardcode either constant, so whoever sets it needs to pick deliberately; (3) `pos_gain`/`vel_gain`/`vel_integrator_gain` have no documented units anywhere in ODrive's docs (neither the API reference nor the tuning guide) - treated as plain dimensionless tuning values; (4) firmware 0.6.x restructured encoders entirely versus older ODrive generations - there is no `axis0.encoder` at all; the onboard magnetic encoder is a separate top-level `odrv0.onboard_encoder0` object, and `axis0.config.load_encoder`/`commutation_encoder` (an `EncoderId` enum) pick which physical encoder feeds `axis0.pos_vel_mapper` (only that mapper's `status` field is kept in the curated channel list, not its full internals) - a stale prose page elsewhere in ODrive's own docs still references `encoder.pos_estimate`/`encoder.pos_circular`, neither of which exists in 0.6.x, left over from an older doc rewrite.
- Cross-platform, OS-signal-independent test stop: `TestCase.check_stop_requested()` (`testcases/base.py`) raises `StopRequested` if `tools/stop_test.py` has left a marker file at `Path(tempfile.gettempdir())/mytest-stop-<test_id>` - checked at the exact same call sites `check_fatal_violation()` already uses (`wait_for()`'s every-10ms tick, `@step`'s entry/exit), so an external stop is noticed with the same promptness, with zero new wiring in any test step. Built specifically because `SIGTERM`/`Popen.terminate()`/`os.kill(..., SIGTERM)` don't reliably reach a process on Windows (see OS compatibility) - this sidesteps OS signals entirely, so it's fully testable on any dev machine with confidence it holds on every target OS identically, unlike a Windows-specific signal-based fix would be. `tools/stop_test.py --test-id <id>` targets a specific test; with no `--test-id`, it discovers the currently-running test's id by subscribing to the run-state stream for one frame (valid since only one test ever runs at a time here), so an operator never needs to know the auto-generated id in advance. Verified end-to-end against `MockOdriveBackend`: `tools/stop_test.py` correctly discovered a running `ManualTest`'s `test_id`, the marker file was noticed and deleted within one poll tick, `StopRequested` propagated through `post_test_teardown()`, and the process exited cleanly with no orphaned subprocess. Does not and cannot help against Task Manager's "End Task" or a bare `taskkill /F` (or `SIGKILL` on POSIX) - those bypass all in-process code by design on every OS; this only works if it's what's actually used to stop a test, which needs to be documented/trained practice, not something enforceable in code.
- Real-hardware motion validated: `EnduranceCycleTest`'s `cycle_position` sequence now runs correctly against the physical ODrive/ydrive rig - the axis cycles between setpoints under closed-loop control and stops cleanly via the operator dashboard's Stop button. Reaching that took fixing one real bug and two hardware-config issues, none in the framework's own plumbing: (1) the spinout-detection power thresholds in `set_tuning_params` had their signs inverted - `MAX_LOAD_SPINOUT_MECHANICAL_THRESHOLD` must be negative and `..._ELECTRICAL_THRESHOLD` positive, backwards from what the ODrive's spinout detector expects - so it tripped almost instantly on any real motion regardless of wiring, calibration, or gains, which is what blocked every earlier motion attempt; (2) the motor needed a fresh calibration whose result had to be explicitly saved to flash (`save_configuration`), since calibration lives in volatile config until saved and a mid-test board reset had been silently reverting it; (3) the position/velocity tuning gains (`MAX_LOAD_POSITION_GAIN`, `MAX_LOAD_VELOCITY_GAIN`) were tuned live against the real motor. The `set_tuning_params` profile is therefore now validated for this specific ILM-E85x26-based mechanism, not the unvalidated placeholder it started as.

- **Telemetry is acquired in tiers where a device makes polling costly, destructive, or pointless (`hardware/cpx400dp/`).** Every prior device could be read the same way for every channel. A SCPI instrument on one serial link cannot, for three independent reasons, and each produced a tier. Each channel is a round-trip, so re-reading a *setpoint* at frame rate spends the link re-learning a value the driver itself last wrote (**cached** tier). Some registers are *read-and-clear*, so polling them destroys the only copy (**not-telemetry** tier - the error registers, consumed by the driver's own post-write check). And a measurement cannot be fresher than the instrument's own reporting rate: the CPX400DP specifies a 4 Hz meter reading rate, so polling voltage and current per frame re-read a register refreshed four times a second - visible in a capture where a decaying output read back as a staircase (**metered** tier, read at 5 Hz and held between reads). What remains is genuine instrument state, polled every frame (**state** tier), which is what caught an OVP trip inside a single frame period. Splitting the meters out halved the median frame cost, 18.9 ms to 9.4 ms, with no loss of measurement freshness.

  All four tiers appear in every published frame, so a recorded row stays self-describing and `verify_channels()` is unaffected. The generalisable rule: **poll each channel at the rate that channel can actually change**, which is a property of the instrument, not of the framework. The cached tier additionally rests on an assumption worth restating rather than burying - nobody turns the front-panel knobs mid-run. If that stops holding, the affected channel moves to the state tier.

- **A driver may refuse a command the instrument would happily accept.** `Cpx400dpBackend` takes optional `max_voltage`/`max_current` ceilings and rejects a setpoint above them before anything reaches the wire. This is not duplicating the instrument's own range checking, which catches only what the *supply* cannot do: 70 V on a 60 V supply is refused by the hardware, while 48 V into a 12 V DUT is accepted, reports no error, and destroys the load. The ceiling is the only layer that knows what the load can survive, and it lives on the backend because a testbed constructing it is the thing that knows. Off by default (`None`), so the driver's out-of-the-box behaviour stays passive.

- **Connect and disconnect adopt device state rather than asserting it.** For the power supply, `connect()` neither enables an output nor disables one it finds already on, and `disconnect()` leaves outputs exactly as they are; the state found at connect is logged so a run records what it inherited. Asserting a safe state on connect would silently de-energize something a person deliberately energized - a bias on a DUT, a soak, a battery under test - and with a single-connection instrument the only other operator is a human at the front panel who would not be expecting it. The one exception is `*CLS` at connect, because the error registers outlive the socket: without clearing them, a driver's first write check can raise on a failure left behind by a process that died earlier. Note the limit of this stance, stated plainly: nothing here survives `SIGKILL`, so energized-state safety belongs to the instrument's own OVP/OCP, which this driver exposes but never sets.

- **Where a mock backend belongs, and where a fake transport belongs instead.** `hardware/odrive/` keeps real and simulated backends side by side because its failure mode is a wrong attribute path, which a mock reproduces faithfully. `hardware/cpx400dp/` has no mock backend, because its failure mode is response parsing - the instrument answers `OVP1?` with `VP1 66.00`, not `OVP1 66.00` - and a backend-level mock would replace precisely the code most likely to be wrong. Its tests substitute the transport instead, so the real parsing runs against replies transcribed byte-for-byte from the instrument. The general rule: mock at the layer *below* the risk, never at the layer that contains it.

## Open implementation decisions (not yet finalized)

- `ManualTest`-via-GUI-issued position/velocity/torque commands haven't been explicitly exercised end-to-end against real hardware yet. Automated motion is now validated through `EnduranceCycleTest` (see Resolved implementation decisions), but issuing ad-hoc motion commands by hand through `tools/manual_gui.py` against the live axis is a separate path that's only been used for read-only inspection so far, not for commanded motion.
- Which real time-series database eventually implements `TelemetryStorage` in place of `WideCsvTelemetryStorage` (candidates: InfluxDB, TimescaleDB), and which report/relational store ingests the verdict records. The *shape* of both is now settled even though neither product is chosen: telemetry ports as a points table tagged by `test_id`/`device`/`channel`, and a verdict ports as one row (with `lifecycle`/`bounds_result` as indexed enum columns) plus one `violations` child table. See The per-run result record.
- **`CYCLE_DUT_POSITION_RULEBOOK`'s two non-fatal bounds now fail every normal run, and need re-specifying.** `current_transient_bound` and `velocity_transient_bound` were authored as informational monitors that trip briefly during acceleration; under the any-violation-fails rule they make a healthy `CycleDutPositionTest` record `COMPLETED/FAIL`. The rule working as decided, but those bounds are mis-specified for it. Fix is a test-engineering call: a `persistence_s` long enough to ignore the transient, limits a healthy run genuinely shouldn't cross, or publish the values as plain state channels instead. `YDRIVE_RULEBOOK` is unaffected - both its bounds are fatal and don't trip normally.
- **The ODrive's own hardware watchdog is plumbed but unused.** `axis_config_enable_watchdog`, `axis_config_watchdog_timeout` and `watchdog_feed` are declared, settable and callable, and nothing anywhere arms or feeds them. So if the testcase process dies mid-motion (`SIGKILL`, `taskkill /F`, a crash), the axis keeps executing its last command indefinitely - the gap this document already concedes software cannot catch, in the one place the architecture says safety belongs (the device's own onboard protection, which for `ydrive` is the *only* onboard protection there is). Decided while designing it, if it gets built: the **test process** must be what feeds it, since a driver-internal feed keeps feeding a live device while the test that owns it is dead. That costs a dedicated `CommandClient` on a background thread (the shared one isn't safe across threads), and `watchdog_timeout` has to exceed `CommandClient`'s own 5 s ceiling - because a feed delayed past it marks that client permanently broken by design, silently stopping the feed and tripping the watchdog on a healthy run. `watchdog_feed` is idempotent, so it's the one action for which rebuilding a timed-out client is safe. Deliberately left device-specific rather than promoted to `HardwareBackend`: no second device has a watchdog, and a hook with one implementation is the speculative generality this project already rejected once. The general expectation stands, though - **a real backend should arm whatever onboard dead-man protection its device offers.**
- **`OdriveBackend._set_axis_state()` writes `requested_state` and never confirms the transition happened.** The ODrive refuses to arm while errors are active or calibration is missing, so a refused arm is a silent no-op: the run proceeds to command positions against an axis still sitting in `IDLE`, and surfaces minutes later as an opaque `TimeoutError` from a move's arrival deadline. This is the "positively confirm, don't assume" principle applied to channels but not to state transitions. The fix is to poll `current_state` after the write and raise naming both the refused state and the current `active_errors`.
- **Nothing watches the ODrive's own error register.** `YDRIVE_RULEBOOK` bounds `board_ibus` and `board_vbus_voltage` only; `active_errors` (which auto-clears when resolved, so it is safe to bound, unlike `disarm_reason`) has no bound, and `clear_errors` has no callers anywhere - so a stale fault from a previous run is never cleared before arming. A fatal `active_errors expected=0` bound would catch every fault the device itself detects: watchdog trips, spinout, overspeed, thermal, encoder faults. Considered and deliberately deferred.
- **Error registers are stored as raw ints.** A recorded failure reads `active_errors: 64`, undecodable without the ODrive enum to hand, which undercuts the record being reviewable later. Decoding them into named channels at read time would fix it - the telemetry server's contract already permits decode, and it is only ever transformation, not evaluation.
- **`OdriveBackend.disconnect()` unconditionally calls `_set_axis_state("IDLE")`** with no guard, on the teardown path. On a faulted axis or a dead USB link that write raises, and `runner.run()` doesn't wrap its `disconnect()` call - so a teardown failure can mask whatever exception was already propagating. The base class now states the contract ("tolerate being called when the device is unreachable"); this implementation doesn't yet meet it.
- Nothing consumes the verdict records yet. There is no reporting UI, no cross-run index, and the operator dashboard shows only its own live status rather than reading the verdict. Deliberately out of scope while the record's shape was being settled; a `tools/` command to list/summarize runs is the obvious next step.
- No cap on a verdict's embedded transition timeline, so a flapping *non-fatal* bound on an indefinite run grows the record without bound - see The per-run result record for why this is currently a latent rather than live risk, and what the fix would be.
- Disk headroom for indefinite runs (~35 MB/hour, ~5.8 GB/week for the real ODrive - measured) is an operational concern with no mechanism behind it: no rotation, no retention policy, and no free-space precheck. The engine dying on a full disk *is* noticed by the running test (its heartbeat goes stale, so the test aborts), but nothing prevents getting there.
- Whether the real ODrive's ~12.6 Hz achieved sample rate (vs the 20 Hz its `SAMPLE_INTERVAL_S` implies, the gap being 111 sequential USB round-trips per frame) is fast enough for the tests that matter, and if not, whether to shorten the interval, read fewer channels per frame, or read hot channels more often than cold ones.
- Whether the DAQ's hardware driver instance specifically should run as a Windows service (likely required, since DewesoftX control is Windows-only) - other device instances aren't tied to that constraint.
- Whether `hardware/runner.py`'s own `asyncio.add_signal_handler`-based shutdown (still a no-op on Windows, silently caught) is worth fixing directly, now that `tools/stop_test.py` (see Resolved implementation decisions) covers the normal path - it would only still matter if something ever stops a driver subprocess directly, bypassing the testbed/DUT abstraction that already handles this correctly via explicit command-channel disconnect. Not needed by any current usage pattern.
- Whether/how MainExecution polls more than one device's telemetry concurrently. *Recording* is no longer the constraint - the engine subscribes to every device and a test declares which ones its run claims - but a test's own live evaluation still watches whichever single telemetry client it's handed. A rulebook spanning two devices' channels would need the evaluator to consume more than one subscription, which is a poller across sockets rather than the single blocking iteration it is today.
- Multi-machine deployment and clock synchronization: today everything runs on one test stand PC, so all processes share one system clock. If the hardware driver(s) ever run on a separate machine from the testcase execution/telemetry engine processes, `frame.t` (the one timestamp shared across the whole pipeline) would need real clock synchronization (e.g. NTP) between machines - not yet a concern, but worth remembering before any multi-machine deployment.
- Extending channel declaration/verification (see Resolved implementation decisions) to the DAQ and power supply. Both already have their own `mock_channels.py` with `TELEMETRY_CHANNELS`/`COMMAND_CHANNELS` declared, but nothing calls `verify_channels()`/`verify_actions()` against them yet, since no test case watches their telemetry today (see the MainExecution polling item above) - the mechanism is generic and proven against the DUT, so this is a one-line addition whenever a test case actually needs it, not a redesign.
- Whether/how a Bound can ever check a channel against another *live* channel's value (a dynamic reference), rather than only a fixed number. `Bound.Comparison.DEVIATES` was tried for exactly this (tracking a commanded setpoint) and deliberately removed - it was the only consumer of the capability in the whole codebase, so keeping it was speculative generality rather than a proven need. The one concrete case that needed it now closed-loops in the test step itself instead (`ExampleDut.get_position()`, polled directly from `cycle_position`) rather than via a Bound - revisit a Bound-level mechanism only if a case emerges that a step-level check can't handle (e.g. a post-hoc Rulebook needing the same comparison, since post-hoc evaluation has no equivalent to a step's live polling).
- ODrive is now wired into a testbed/test case (`YdriveTestbed`/`BaseYdriveTest`, for `ydrive`) rather than standalone, but that test case is still bones-only - see the next bullet.
- Building the first real (non-mock) backend surfaced robustness gaps no mock could ever exercise, since mocks never fail this way: `runner.py`'s `run()` used to silently discard a server task's exception (`asyncio.gather(..., return_exceptions=True)` without checking the result), so a real `stream_samples()` raising (e.g. a lost USB connection) would kill telemetry while the process kept running with the command server still up, unnoticed. `run()` now treats a server task dying on its own the same as a shutdown signal (cancel the other task, disconnect, log which task failed and why, re-raise so the process actually exits) - this is shared code, so it protects every future real backend, not just ODrive's. Also added: a `discovery_timeout_s` on `OdriveBackend.connect()` (its `odrive.find_any()` call blocks indefinitely with no timeout by default - a missing/unpowered device would otherwise hang the `connect` command forever), a distinction in `_read_all_channels()` between a channel genuinely absent from this hardware config (`AttributeError`, logged once, reported as `None`) versus any other failure (left to propagate, so the `runner.py` fix above can actually catch a real disconnect instead of it being silently swallowed), and basic logging (connect/disconnect/missing-channel warnings) where there had been none. All four were verified with synthetic tests (a stub `odrive` module, a stub attribute-graph object, a backend whose `stream_samples()` raises on purpose) rather than real hardware, which isn't available yet - see `hardware/README.md`'s Verified section for what was actually exercised.
- `OdriveBackend` has now been verified against a physical ODrive for connect/read (see Resolved implementation decisions), confirming its attribute paths hold in reality, not just against ODrive's autogenerated 0.6.x API reference. What's still unconfirmed: the exact `AxisState`/`ControlMode` enum member names and the error/fault bitmask semantics (`active_errors`/`disarm_reason`/`detailed_disarm_reason`) haven't been exercised through an actual state transition or fault condition yet, only read at rest (`IDLE`, no errors) - these were the least-documented part of the surface and still need verification via `odrivetool` or an actual armed/faulted run before fully relying on them.
- **Whether a fatal bound violation actually needs to stop MainExecution's own running code, and if so, how.** `LiveRulebookRunner.evaluate()` raises `FatalBoundViolation` the instant a fatal bound violates, but this is *not* automatically propagated into MainExecution's thread - Python exceptions don't cross threads on their own, and there's no safe way to force an *already-running, different* thread to stop (the unsafe options - async exception injection, OS signals - were rejected; see the signal-based watchdog discussion below for exactly why signals specifically don't work here). `LiveRulebookRunner._run()` (its own background thread) catches it, logs, stops evaluating, and stores the exception in a plain `fatal_violation` attribute.

  This project's original decision here (superseded, kept for history) was to reject a cooperative-checkpoint approach entirely, in favor of keeping test-authored step code fully free of any fatal-bound awareness - `example_dut`'s original `cycle_position` reflected that: a plain elapsed-time loop with zero evaluation awareness. That decision was later revisited for `ydrive` and generalized onto `TestCase` itself (`testcases/base.py`): `TestCase.check_fatal_violation()` raises `self.runner.fatal_violation` if set (a no-op otherwise); `TestCase.wait_for()` calls it every tick of a paced wait; the `@step` decorator (`testcases/step.py`, shared by *every* test case, not just `ydrive`) calls it once at step entry and once at step exit. So today, a fatal violation genuinely does stop MainExecution - but only at those checkpoints, not instantaneously everywhere.

  **Known, still-unaddressed gap:** a step that runs a long time without itself calling `check_fatal_violation()` (directly, or via `wait_for()`) - one big blocking hardware call, or a raw `time.sleep()` instead of `test_case.wait_for()` - won't be interrupted until it returns on its own and the step-exit check fires. A `signal.alarm()`/`signal.setitimer()`-based watchdog was designed and considered specifically to close this (a signal handler can interrupt a thread's code without that code cooperating at all, unlike polling), and explicitly rejected: Python only permits registering/delivering signals on the interpreter's *main* thread, and this codebase already runs `TestCase.run()` off the main thread in three existing places today - `telemetry_engine/demo_evaluation_run.py`, `demo_storage_run.py`, and `demo_aggregator_run.py`, all via `await asyncio.to_thread(CycleDutPositionTest(...).run)`, needed so a synchronous, fully-blocking `.run()` call doesn't freeze the event loop those demos also run an aggregator/evaluator task on. A signal-based watchdog would silently stop protecting a test the moment it runs that way - not a rare edge case here, but an already-exercised pattern. Until this gap is addressed some other way, any future long-running step is expected to poll on its own; there is no automatic safety net for one that doesn't.

  Also still open: whether a hardware-safing action taken at evaluation time (if one is ever added) could be immediately undone by MainExecution's own still-running, now-stale command logic reverting the system right back to the condition being safed against, in the window between a fatal violation occurring and the next checkpoint. Remember: none of this is the safety layer of record regardless - that's the hardware's own onboard interlock (see Real-time tiers above), which this entire mechanism supervises but never replaces.

- **The CPX400DP is a driver with no owner.** `hardware/cpx400dp/` exists and is verified against the real instrument, but no testbed starts its process and no test declares `cpx400dp` in its `DEVICES`, so its frames would go to the per-session record rather than into a run directory. Wiring it into a testbed is a deliberate follow-on: adding a device to `YdriveTestbed.DEVICES` changes what every existing ydrive run records, which deserves its own reviewable change. Whether it belongs there specifically is an open question of fact - the supply was found parked at 47.62 V / 20.202 A, which looks like an ODrive DC bus setting, but that has not been confirmed.

- **The CPX400DP's address is not stable, and nothing detects it moving.** `NETCONFIG?` reports DHCP, but the segment has no DHCP server, so the instrument self-assigned a link-local address (169.254.229.133). It moves if a DHCP server appears or on a collision. The driver defends against the dangerous half of this - `connect()` checks the model in `*IDN?` and refuses anything that is not a CPX400DP, so it cannot stream another instrument's replies under this device name - but it cannot *find* the instrument again. Options not yet chosen: a static address set through the instrument's web interface (the simplest, and the recommendation), a per-testbed config module (the shape `testbeds/example_testbed/config/` was reserved for and never filled), or VXI-11/mDNS discovery, which finds "a TTi instrument on this segment" rather than a specific serial number and so is a weaker guarantee than the ODrive's `find_any(serial_number=...)`.

- **Two CPX400DP limit-status bits remain unverified**, down from four: `tripped_latching_<n>` (bit 6) and `in_power_limit_<n>` (bit 4). Nothing reachable from software provoked either - notably, neither an OVP nor an OCP trip sets bit 6, so both are soft trips. `in_cc_<n>`, `tripped_ov_<n>` and `tripped_oc_<n>` have since been verified against real hardware (constant current and an over-current trip into a deliberate short, an over-voltage trip into bare terminals), and all four measured bits behave as **levels** rather than the edge events the manual describes.

- **Recovering from a trip on the CPX400DP is device-specific and undocumented, and no framework-level abstraction covers it.** `TRIPRST` is documented as "attempt to clear all trip conditions" and was measured to clear nothing; worse, the two trips need different recovery - OVP clears when its threshold is raised back above the setpoint, OCP clears only on an explicit output-off command and ignores both a raised threshold and `TRIPRST`. This is currently documented rather than encoded: there is no `recover_from_trip()` action, so a test author has to know it. Whether device-specific recovery sequences belong in the driver, in a testbed, or in a test step is an open question that this is the first instance of - the ODrive's `clear_errors()` happens to be a single call, which is why it never came up.
